CORRECTION 1 — server-side teacher scoping:
  New backend module `apps/api/src/teacher-portal/` — `GET /teacher/me`,
  `GET /teacher/courses`, `GET /teacher/sessions`, and (added beyond the
  reviewer's minimum, to close the same class of gap for the detail view)
  `GET /teacher/sessions/:id`. Every method derives the caller's
  TeacherProfile from the authenticated JWT (`@CurrentUser()`), never from
  a client-supplied id, and the Prisma queries themselves are scoped
  (`where: { primaryTeacherId: teacherId }` /
  `where: { teachers: { some: { teacherId } } }` /
  `where: { id, teachers: { some: { teacherId } } }`) — the database never
  returns another teacher's rows in the first place. Reuses the exact same
  `courseInclude`/`sessionInclude`/`teacherInclude` shapes
  CoursesService/SessionsService/TeachersService already used (each now
  exported rather than duplicated). The frontend's `teacher/page.tsx` and
  `teacher/sessions/*` pages now call these endpoints instead of
  downloading `/admin/courses`/`/admin/sessions` and filtering client-side
  — `hooks/use-my-teacher-profile.ts` (the client-side identity-matching
  workaround) is deleted entirely. See sections G/O/U.

CORRECTION 2 — active-session 401 invalidation:
  `lib/api-client.ts` gained a small pub/sub (`onUnauthorized`/
  `notifyUnauthorized`): any authenticated request (`skipAuth` not set)
  that receives 401 clears the stored token and notifies every listener.
  `AuthContext` subscribes once and sets `user: null` on notification,
  which is exactly what makes `ProtectedRoute` redirect to `/login` on
  its next render — no page or hook handles 401 individually.
  `POST /auth/login` is always called with `skipAuth: true`, so an
  ordinary invalid-credentials 401 there never reaches this mechanism.
  See sections D/N/U.

CORRECTION 3 — Offering discovery for Subscription Access:
  New minimal backend module `apps/api/src/offerings/` —
  `GET /admin/offerings` (list) and `GET /admin/offerings/:id`, ADMIN-only,
  read-only (no create/update/delete — Offering rows are not created
  through any API in this codebase, and adding that was explicitly out of
  scope for this correction). The Subscription Access admin page's raw
  Offering-UUID text field is replaced with a real `<select>` populated
  from this endpoint, and the grants list now shows the Offering's name
  instead of its bare id. See sections G/O/U.

DOCUMENTATION CORRECTION:
  Section A previously said window-exception operations were "delivered"
  — corrected below to match sections O/S, which already correctly
  described them as client-function-only, no UI. A new automated
  assertion (`teacher/sessions/[id]/page.test.tsx`) now proves the
  TEACHER session detail page renders no ADMIN-only lifecycle/recording/
  teacher-assignment mutation control — previously this was verified only
  by reading the source, per section S's own disclosed gap.

CORRECTION 4 (FINAL SECURITY CORRECTION) — ADMIN routes are ADMIN-only:
  The three corrections above added dedicated, server-side-scoped
  `/teacher/*` routes, but the external reviewer correctly identified that
  this alone did not close the gap: the legacy broad ADMIN-namespaced
  routes those `/teacher/*` routes were meant to replace — `GET
  /admin/courses[/:id]`, `GET /admin/teachers[/:id]`,
  `GET /admin/sessions[/:id]`, `GET /admin/sessions/:id/teachers`, and
  (found during the audit and closed for consistency, since the "preferred
  rule" the reviewer stated is unconditional) `GET
  /admin/{grade-levels,subjects,academic-terms}[/:id]` — were all still
  `@Roles('ADMIN', 'TEACHER')`. A TEACHER could therefore bypass the new
  scoped path entirely simply by calling the old broad route directly,
  which the RolesGuard would still accept. Every one of these routes is
  now `@Roles('ADMIN')` only — six controllers, thirteen route
  decorators, one line each (see section U for the exact diffs). TEACHER
  attendance reads (`GET /teacher/attendance/sessions/:id`, already scoped
  by `assertTeacherAssignedToSession`) and the new `/teacher/*` routes
  themselves are unaffected — this correction only removes an
  authorization grant that had become redundant and unsafe, it adds no
  new restriction to anything a teacher actually needs. Three pre-existing
  RBAC tests that asserted "TEACHER can read the teacher/session/
  grade-level list" were updated to assert 403 instead (they were testing
  the exact behavior this correction removes); a new dedicated spec,
  `admin-routes-teacher-scoping.http.spec.ts`, proves end-to-end — real
  guards, real controllers — that TEACHER now gets 403 from the broad
  courses/teachers/sessions routes, ADMIN continues to get 200 from the
  same routes, and the scoped `/teacher/me`/`/teacher/courses`/
  `/teacher/sessions` routes continue to work for TEACHER while being
  rejected for ADMIN (role checks remain mutually exclusive, not
  additive). See section U for the complete new spec and the controller
  diffs.

C. FRONTEND ARCHITECTURE
================================================================================

Layering, bottom to top:

  1. `config/api.ts` (pre-existing from Phase 2G) — `API_BASE_URL` from
     `NEXT_PUBLIC_API_URL`, falling back to `http://localhost:3001` for
     local development. Never hardcoded elsewhere.
  2. `lib/api-client.ts` — the ONLY place that calls `fetch`. Prefixes
     every path with `/api/v1` (matching the backend's actual global
     prefix, `apps/api/src/main.ts`), attaches the bearer token from
     storage unless `skipAuth` is set (login/register), and normalizes
     every non-2xx response and every network failure into a single
     `ApiError` type with a clean, backend-or-generic message — never a
     raw stack trace, never a raw `TypeError`.
  3. `lib/endpoints.ts` — typed, named functions per resource, grouped by
     backend module (`authApi`, `sessionsApi`, `attendanceApi`, ...). No
     page ever constructs a URL string itself.
  4. `hooks/use-fetch.ts` / `hooks/use-async-action.ts` — the two generic
     hooks every read and every mutation in the app uses. `useFetch`
     exposes exactly `{ data, isLoading, error, status, refetch }`;
     `useAsyncAction` exposes `{ run, isSubmitting, error }` with a
     ref-based in-flight guard preventing duplicate submission. Neither
     is page-specific — this is what stops API-fetching logic from being
     duplicated per page (an explicit brief requirement).
  5. `context/auth-context.tsx` — session state, backed by the above.
  6. `components/guards/protected-route.tsx` + `components/shell/*` —
     role-aware routing and the shared shell, built on the context.
  7. Per-role route trees under `app/{admin,teacher,learner}/*`, each
     wrapped by a `layout.tsx` that composes `ProtectedRoute` +
     `AppShell`.

Loading/empty/error/forbidden states are shared components
(`components/ui/states.tsx`) used identically everywhere — a page never
writes its own spinner or its own "something went wrong" text.

Local development remains unaffected: `NEXT_PUBLIC_API_URL` defaults to
`http://localhost:3001` when unset, exactly as it did in Phase 2G;
running `pnpm dev` in `apps/web` alongside the API's `pnpm dev` in
`apps/api` works with no configuration.

D. AUTHENTICATION IMPLEMENTATION
================================================================================

Built directly against the existing backend semantics (Phase 2C/2G),
never redesigned:

  - Login: `POST /auth/login` with `{ email, password }`. On success, the
    access token is stored (see section N for the storage trade-off) and
    the returned `SanitizedUser` becomes the session; the caller is
    redirected to `homeRouteForRole(user.role)`.
  - Login failure: the backend's own message (`"Invalid email or
    password"` for both wrong-password and nonexistent-account — the
    backend's own anti-enumeration design, unchanged) is rendered
    verbatim via `role="alert"`; no redirect happens.
  - Session restoration: on mount, `AuthProvider` reads any stored token
    and calls `GET /auth/me`; a 401 (expired, invalid, or the account is
    now inactive/deleted) clears the stored token and leaves the user
    logged out — the same outcome the backend produces for any of those
    cases, deliberately indistinguishable to the frontend just as it is
    to the backend's own callers.
  - Logout: clears the stored token and the in-memory user, then the
    caller navigates to `/login`. No server-side call exists for logout
    in this backend (JWTs are stateless, no revocation endpoint) — this
    is the correct, complete client-side logout for the auth model as
    built.
  - Role-based redirect after login: `homeRouteForRole` (`nav-config.ts`)
    — ADMIN → `/admin`, TEACHER → `/teacher`, LEARNER → `/learner`.
  - Protected routes: see section E.
  - No OAuth, social login, MFA, or password reset were added — none of
    these exist in the backend, and the brief explicitly excludes adding
    them here.

E. ROLE-AWARE ROUTING / RBAC UX
================================================================================

`components/guards/protected-route.tsx` wraps every page under
`app/{admin,teacher,learner}/layout.tsx` with an `allowedRoles` check:
  - No authenticated user → redirect to `/login`.
  - Authenticated but wrong role → redirect to `/unauthorized`.
  - Otherwise → render.

This is explicitly UX-only (documented in the component's own comment,
section N) — the backend's `JwtAuthGuard`/`RolesGuard` on every endpoint
remain the actual authorization boundary regardless of what this
component decides; a wrong-role user who somehow reached a page would
still have every API call rejected with 401/403 by the real backend.

`components/shell/nav-config.ts`'s `NAV_BY_ROLE` is the single source of
truth for what each role can navigate to via the shell — ADMIN sees every
administrative section, TEACHER sees only `/teacher` and
`/teacher/sessions`, LEARNER sees only `/learner`. Tested directly
(`nav-config.test.ts`) against the actual exported config, not against
rendered markup, so the RBAC navigation contract cannot silently drift
from what the test asserts.

    full list+create+rename+delete via the shared `NamedEntityManager`

    subjects}`.
  - Academic Terms (`admin/academic-terms`): list+create (name + start/

  - Courses (`admin/courses`): list+create, with subject/grade-level/

H. TEACHER WORKSPACE
================================================================================

Focused entirely on teaching operations, never system governance:

  [CORRECTED per Correction 4 — the final security correction] As of this
  correction round, `GET /admin/courses`, `GET /admin/teachers`,
  `GET /admin/sessions`, and `GET /admin/sessions/:id/teachers` are ADMIN-
  only at the backend role-guard level — a TEACHER now gets 403 from every

  from the frontend's perspective before this correction (the UI never

  token and no frontend involved at all. That bypass is now closed at its
  source, not merely avoided by the UI.

  - `teacher` (overview): [CORRECTED per external review Correction 1]
    assigned courses and upcoming sessions, now read from
    `GET /teacher/courses` and `GET /teacher/sessions`

    backend itself scopes to the caller's own TeacherProfile, resolved
    server-side from the JWT via `@CurrentUser()`. The prior approach
    (downloading the full `GET /admin/courses`/`GET /admin/sessions`

    of whose data it actually was. See section U for the exact scoped
    Prisma queries.
  - `teacher/sessions`: every session the caller is assigned to, any
    role — now `GET /teacher/sessions` directly, no client-side filter.
  - `teacher/sessions/[id]`: [CORRECTED per Correction 1] now reads
    `GET /teacher/sessions/:id`, which scopes the lookup itself
    (`where: { id, teachers: { some: { teacherId } } }`) — a session this
    teacher is not assigned to reads as 404 here, closing a real gap the
    correction round found: `GET /admin/sessions/:id` is nominally
    TEACHER-permitted at the role-guard level but performed NO assignment

================================================================================
I. LEARNER WORKSPACE
================================================================================

Built entirely around the Session — the core teaching object, per the
frozen domain design:

  - `learner`: every entitled session (`GET /learner/sessions`), with a
    "Next class" highlight for the soonest non-canceled upcoming session,
    and a plain list below.
  - `learner/sessions/[id]`: course, schedule, status; a "Live class"
    card and a "Recording" card, an attendance card, and — only when a
    recording exists — a viewing-progress report form (section L).

DeliveryMode is respected strictly, and NEVER inferred in the browser:
  - "Live class": the card renders "Join live class" (linking to the
    real `liveMeetingUrl`) if and only if
    `session.liveMeetingUrl.length > 0`. The backend redacts this field
    to `''` for any learner whose entitlement does not affirmatively
    resolve to `LIVE_AND_RECORDED` — `LearnerPortalService.
    redactLiveAccess`, Phase 2G Correction 3, fails closed. The frontend
    has no DeliveryMode value, no offering lookup, and no entitlement
    logic of its own anywhere in this page — it reads one field and
    branches on whether it is empty. A RECORDED_ONLY-entitled learner
    therefore structurally cannot see live access information, and a
    learner whose entitlement-origin data is unresolvable (the backend's
    own fail-closed case) is treated identically to RECORDED_ONLY —
    tested directly (`page.test.tsx`).
  - "Recording": rendered if and only if `session.recording` is non-null
    — both DeliveryMode values include recorded access, so there is no
    redaction to reproduce on this side (matches the Phase 2G review's
    own documented reasoning for why no symmetric RECORDED gate exists).

Attendance is rendered in human language via `AttendanceStatusBadge` —
"Pending" / "Present (Live)" / "Present (Recorded)" / "Absent" — never
the raw enum tokens, and the coverage figures shown (`liveCoverageMs`,
`recordedCoverageSeconds`) are exactly what
`GET /learner/sessions/:id/attendance` returns, converted to minutes for
display only; nothing is computed toward a threshold client-side (see
section K).

================================================================================
J. SESSION-CENTRIC UX
================================================================================

There is exactly one Session concept in the frontend, matching the frozen
design's "live and recorded participation are two pathways to the SAME
Session, not two parallel systems": one `SessionWithRelations`/
`LearnerVisibleSession` type, one detail page per role, one card per
session in every list. Live and recorded access are simply two
conditionally-rendered sections of the same session detail page (section
I) — never two separate routes, cards, or data-fetch calls for "the live
version" and "the recorded version" of a class.

Lifecycle states are rendered as `SessionStatusBadge`: "Scheduled",
"Live now", "Completed" (for the frozen `ENDED` value — there is no
separate `COMPLETED` enum member; "Completed" is a UI label only, not an
invented backend state), "Canceled". Replacement relationships are
surfaced as one plain sentence ("This session is a replacement for a
previously canceled session") on the admin session detail page rather
than exposing `replacementForSessionId`'s raw UUID anywhere in the UI.

================================================================================
K. ATTENDANCE UX
================================================================================

`components/attendance-status-badge.tsx` is the only place attendance
status is rendered anywhere in the app (admin session detail, teacher
session detail, learner session detail) — one component, one behavior:
`PENDING` → "Pending", `ABSENT` → "Absent", `PRESENT` → "Present (Live)"
or "Present (Recorded)" depending on the backend's own `completionMode`.
Tested directly, including an explicit assertion that the raw enum token
"PRESENT" never appears verbatim in the rendered output.

The frontend performs NO independent attendance computation anywhere:
no 50%-of-scheduled-duration math, no 100%-coverage math, no cutoff
comparison, no exception-precedence logic, no finalization logic. Every
value shown — `status`, `completionMode`, `liveCoverageMs`,
`recordedCoverageSeconds` — is read directly from
`GET /learner/sessions/:id/attendance` or
`GET /{admin,teacher}/attendance/sessions/:id` and displayed, never
recomputed. The backend (Phase 2F attendance engine, unchanged by this
milestone) remains the sole authority for all of the above.

L. RECORDING INTEGRATION BOUNDARY

No video player, no fake playback UI, no simulated buffering/progress

N. SECURITY REVIEW
================================================================================

  - [NEW per external review Correction 4 — the final security
    correction] Broad-route bypass of server-side scoping: this is a
    genuine backend authorization finding, not a frontend-only concern —
    it is documented here because the original Phase 3 review's own
    section R/U material is what made the gap visible (disclosing that
    `GET /admin/sessions/:id` performed no assignment check). A TEACHER
    holding a valid bearer token could call `GET /admin/courses`,
    `GET /admin/teachers`, `GET /admin/sessions`, or
    `GET /admin/sessions/:id/teachers` directly (curl, Postman, a modified
    client — anything that can set an Authorization header) and receive
    every course/teacher/session in the school, or any session's full
    teacher roster by id, entirely bypassing the new `/teacher/*` scoping
    — because the RolesGuard itself still granted TEACHER access to
    those routes. Frontend-side correctness (Correction 1) was never
    sufficient on its own for this reason: UX-level routing cannot close
    a gap that exists in the API's own role guard. Closed by removing
    TEACHER from the `@Roles(...)` decorator on every read route of six
    ADMIN-namespaced controllers (courses, teachers, sessions, plus
    grade-levels/subjects/academic-terms for consistency with the stated
    "ADMIN-only" rule) — see section U for the exact diffs and the new
    `admin-routes-teacher-scoping.http.spec.ts` proving the fix with real
    guards.
  - [NEW per external review Correction 2] Active-session invalidation:
    prior to this correction, a token that expired or became invalid
    (account deactivated) WHILE the app was already open left React auth
    state populated indefinitely — every subsequent authenticated request
    would keep failing with 401 without the app ever noticing, since only
    startup-time restoration handled a bad token. `lib/api-client.ts` now
    centralizes this: any authenticated request's 401 clears the stored
    token and notifies `AuthContext` via `onUnauthorized`, which sets
    `user: null` — `ProtectedRoute` then redirects to `/login` on its very
    next render, exactly as if the user had logged out. This is the one
    mechanism handling it; no individual page or hook has its own 401
    logic. Verified this cannot misfire on an ordinary login failure:
    `POST /auth/login` always passes `skipAuth: true`, so its 401 never
    reaches this code path at all — proven directly by
    `api-client.test.ts` and `auth-context.test.tsx`.
  - Token storage: the access token is stored in `localStorage`
    (`lib/api-client.ts`, `ACCESS_TOKEN_STORAGE_KEY`). This is the one
    deliberate trade-off in this milestone, documented directly in the
    source: the backend issues a bearer token in the login response
    body, not an httpOnly cookie, and changing that is a backend
    authentication-semantics change explicitly out of scope for a
    frontend milestone ("use the existing backend authentication
    semantics rather than redesigning authentication"). `localStorage`
    is therefore the only mechanism available without that backend
    change. Mitigations actually in place: the token is never rendered
    into the DOM, never logged, never included in any error message, and
    is read through exactly one function (`getStoredAccessToken`); this
    app renders no user-controlled HTML via `dangerouslySetInnerHTML`
    anywhere, which is the primary way a stored token becomes exploitable
    via XSS. See section S for what a future hardening pass could do
    instead (httpOnly cookie issuance) — that is a backend change, not
    something this milestone could do unilaterally.
  - Accidental secret exposure: grepped the entire `apps/web/src` tree —
    no `DATABASE_URL`, `JWT_SECRET`, or any Railway/server-only variable
    is referenced anywhere in frontend code. Only `NEXT_PUBLIC_API_URL`
    is read, which is the one variable explicitly designed to be public
    (inlined into the browser bundle by Next.js itself).
  - Role-route leakage: `ProtectedRoute` renders `null` (not even a
    flash of the protected layout) while a redirect is in flight for
    both the unauthenticated and wrong-role cases — verified directly by
    `protected-route.test.tsx` asserting the protected children are never
    in the document in either case.
  - IDOR assumptions: every learner-facing and teacher-facing call
    resolves identity from the authenticated session (`useAuth().user`)
    server-side — the frontend never sends a learnerId/teacherId the
    backend would need to trust blindly. [CORRECTED per Correction 1]
    Teacher course/session/session-detail reads are now backend-scoped by
    `TeacherPortalService` (deriving the caller's TeacherProfile from the
    JWT and filtering the Prisma query itself), closing what was
    previously a UX-only, non-enforcing client-side filter; teacher
    attendance reads remain scoped via `assertTeacherAssignedToSession` as
    before. Every write that could affect another user's data is
    validated against `req.user` server-side regardless of what this
    frontend sends.
  - XSS-prone rendering: no `dangerouslySetInnerHTML` anywhere in this
    milestone's code (grepped). All backend-sourced text (names, titles,
    error messages) is rendered as ordinary React children, which React
    escapes by default.
  - Unsafe external URLs: `liveMeetingUrl` and `recordingUrl` are
    rendered as `<a target="_blank" rel="noopener noreferrer">` —
    `rel="noopener noreferrer"` prevents the opened page from getting a
    `window.opener` reference back to this app (reverse-tabnabbing).
    Both URLs are ADMIN-entered (validated server-side by `@IsUrl` on the
    relevant DTOs) rather than arbitrary learner input.
  - Sensitive API error rendering: `ApiError.message` is either the
    backend's own (already user-safe — Nest never returns a stack trace
    in a response body) validation/conflict message, or this app's own
    generic fallback ("Something went wrong. Please try again." /
    "Could not reach the TUBI server...") for a network failure — never
    a raw `Error.stack` or a raw `TypeError` message.

import { API_BASE_URL } from '@/config/api';

const API_VERSION_PREFIX = '/api/v1';
const ACCESS_TOKEN_STORAGE_KEY = 'tubi.accessToken';

export class ApiError extends Error {
  readonly status: number;

  constructor(status: number, message: string) {
    super(message);
    this.name = 'ApiError';
    this.status = status;
  }
}

export function getStoredAccessToken(): string | null {
  if (typeof window === 'undefined') return null;
  return window.localStorage.getItem(ACCESS_TOKEN_STORAGE_KEY);
}

export function setStoredAccessToken(token: string): void {
  if (typeof window === 'undefined') return;
  window.localStorage.setItem(ACCESS_TOKEN_STORAGE_KEY, token);
}

export function clearStoredAccessToken(): void {
  if (typeof window === 'undefined') return;
  window.localStorage.removeItem(ACCESS_TOKEN_STORAGE_KEY);
}

type UnauthorizedListener = () => void;
const unauthorizedListeners = new Set<UnauthorizedListener>();

export function onUnauthorized(listener: UnauthorizedListener): () => void {
  unauthorizedListeners.add(listener);
  return () => unauthorizedListeners.delete(listener);
}

function notifyUnauthorized(): void {
  for (const listener of unauthorizedListeners) listener();
}

interface RequestOptions {
  method?: 'GET' | 'POST' | 'PATCH' | 'DELETE';
  body?: unknown;
  skipAuth?: boolean;
}

function extractMessage(payload: unknown, fallback: string): string {
  if (payload && typeof payload === 'object' && 'message' in payload) {
    const message = (payload as { message?: unknown }).message;
    if (typeof message === 'string') return message;
    if (Array.isArray(message)) return message.filter((m) => typeof m === 'string').join(' ');
  }
  return fallback;
}

export async function apiRequest<T>(path: string, options: RequestOptions = {}): Promise<T> {
  const { method = 'GET', body, skipAuth = false } = options;

  const headers: Record<string, string> = { Accept: 'application/json' };
  if (body !== undefined) headers['Content-Type'] = 'application/json';

  if (!skipAuth) {
    const token = getStoredAccessToken();
    if (token) headers.Authorization = `Bearer ${token}`;
  }

  let response: Response;
  try {
    response = await fetch(`${API_BASE_URL}${API_VERSION_PREFIX}${path}`, {
      method,
      headers,
      body: body !== undefined ? JSON.stringify(body) : undefined,
    });
  } catch {
    throw new ApiError(0, 'Could not reach the TUBI server. Check your connection and try again.');
  }

  if (response.status === 204) {
    return undefined as T;
  }

  const isJson = response.headers.get('content-type')?.includes('application/json') ?? false;
  const payload: unknown = isJson ? await response.json().catch(() => null) : null;

  if (!response.ok) {
    if (response.status === 401 && !skipAuth) {
      // The token this request just carried is no longer valid — clear it
      // and tell every listener (there is exactly one: AuthContext) so the
      // whole app treats this precisely like a fresh logout, regardless of
      // which page or hook happened to make the request that discovered it.
      clearStoredAccessToken();
      notifyUnauthorized();
    }

    throw new ApiError(response.status, extractMessage(payload, `Request failed (${response.status})`));
  }

  return payload as T;
}

export const api = {
  get: <T>(path: string) => apiRequest<T>(path),
  post: <T>(path: string, body?: unknown, options?: Pick<RequestOptions, 'skipAuth'>) =>
    apiRequest<T>(path, { method: 'POST', body, ...options }),
  patch: <T>(path: string, body?: unknown) => apiRequest<T>(path, { method: 'PATCH', body }),
  delete: <T>(path: string) => apiRequest<T>(path, { method: 'DELETE' }),
};

'use client';

import { createContext, useCallback, useContext, useEffect, useMemo, useState } from 'react';
import type { ReactNode } from 'react';

import { authApi } from '@/lib/endpoints';
import {
  clearStoredAccessToken,
  getStoredAccessToken,
  onUnauthorized,
  setStoredAccessToken,
} from '@/lib/api-client';
import type { SanitizedUser } from '@/lib/types';

interface AuthContextValue {
  user: SanitizedUser | null;
  isLoading: boolean;
  login: (email: string, password: string) => Promise<SanitizedUser>;
  logout: () => void;
}

const AuthContext = createContext<AuthContextValue | null>(null);

export function AuthProvider({ children }: { children: ReactNode }) {
  const [user, setUser] = useState<SanitizedUser | null>(null);
  const [isLoading, setIsLoading] = useState(true);

  useEffect(() => {
    let cancelled = false;

    async function restoreSession() {
      const token = getStoredAccessToken();
      if (!token) {
        if (!cancelled) setIsLoading(false);
        return;
      }

      try {
        const restoredUser = await authApi.me();
        if (!cancelled) setUser(restoredUser);
      } catch {
        clearStoredAccessToken();
        if (!cancelled) setUser(null);
      } finally {
        if (!cancelled) setIsLoading(false);
      }
    }

    void restoreSession();

    return () => {
      cancelled = true;
    };
  }, []);

  const login = useCallback(async (email: string, password: string) => {
    const { accessToken, user: loggedInUser } = await authApi.login(email, password);
    setStoredAccessToken(accessToken);
    setUser(loggedInUser);
    return loggedInUser;
  }, []);

  const logout = useCallback(() => {
    clearStoredAccessToken();
    setUser(null);
  }, []);

  // Phase 3 external review Correction 2: the ONE centralized place a 401
  // from an already-authenticated request invalidates the local session.
  // A POST /auth/login credential failure never reaches this listener —
  // that call is always made with skipAuth: true.
  useEffect(() => onUnauthorized(() => setUser(null)), []);

  const value = useMemo(
    () => ({ user, isLoading, login, logout }),
    [user, isLoading, login, logout],
  );

  return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>;
}

export function useAuth(): AuthContextValue {
  const context = useContext(AuthContext);
  if (!context) {
    throw new Error('useAuth must be used within an AuthProvider');
  }
  return context;
}

'use client';

import { useRouter } from 'next/navigation';
import { useEffect } from 'react';
import type { ReactNode } from 'react';

import { useAuth } from '@/context/auth-context';
import { LoadingState } from '@/components/ui/states';
import type { RoleName } from '@/lib/types';

export function ProtectedRoute({
  children,
  allowedRoles,
}: {
  children: ReactNode;
  allowedRoles?: RoleName[];
}) {
  const { user, isLoading } = useAuth();
  const router = useRouter();

  useEffect(() => {
    if (isLoading) return;
    if (!user) {
      router.replace('/login');
      return;
    }
    if (allowedRoles && !allowedRoles.includes(user.role)) {
      router.replace('/unauthorized');
    }
    // eslint-disable-next-line react-hooks/exhaustive-deps
  }, [isLoading, user, router]);

  if (isLoading) {
    return <LoadingState label="Checking your session…" />;
  }

  if (!user) {
    return null;
  }

  if (allowedRoles && !allowedRoles.includes(user.role)) {
    return null;
  }

  return <>{children}</>;
}

import { ForbiddenException, Injectable, NotFoundException } from '@nestjs/common';

import { courseInclude, type CourseWithRelations } from '../courses/courses.service.js';
import { PrismaService } from '../prisma/prisma.service.js';
import { sessionInclude, type SessionWithRelations } from '../sessions/sessions.service.js';
import { teacherInclude, type TeacherWithUser } from '../teachers/teachers.service.js';

@Injectable()
export class TeacherPortalService {
  constructor(private readonly prisma: PrismaService) {}

  private async resolveTeacherProfileId(userId: string): Promise<string> {
    const profile = await this.prisma.teacherProfile.findUnique({ where: { userId } });

    if (!profile) {
      throw new ForbiddenException('No teacher profile is associated with this account');
    }

    return profile.id;
  }

  async getMyProfile(userId: string): Promise<TeacherWithUser> {
    const teacherId = await this.resolveTeacherProfileId(userId);

    return this.prisma.teacherProfile.findUniqueOrThrow({
      where: { id: teacherId },
      include: teacherInclude,
    });
  }

  async listMyCourses(userId: string): Promise<CourseWithRelations[]> {
    const teacherId = await this.resolveTeacherProfileId(userId);

    return this.prisma.course.findMany({
      where: { primaryTeacherId: teacherId },
      include: courseInclude,
      orderBy: { title: 'asc' },
    });
  }

  async listMySessions(userId: string): Promise<SessionWithRelations[]> {
    const teacherId = await this.resolveTeacherProfileId(userId);

    return this.prisma.session.findMany({
      where: { teachers: { some: { teacherId } } },
      include: sessionInclude,
      orderBy: { startTime: 'asc' },
    });
  }

  /**
   * A single session detail read, scoped exactly like listMySessions.
   * GET /admin/sessions/:id is also nominally TEACHER-permitted at the
   * role-guard level, but SessionsService.findOne performs no assignment
   * check at all — any TEACHER could otherwise read any session's detail
   * by id. This method is what the teacher-facing session detail page
   * uses instead: a session this teacher is not assigned to reads as 404,
   * not merely "not linked to from their own list."
   */
  async getMySession(userId: string, sessionId: string): Promise<SessionWithRelations> {
    const teacherId = await this.resolveTeacherProfileId(userId);

    const session = await this.prisma.session.findFirst({
      where: { id: sessionId, teachers: { some: { teacherId } } },
      include: sessionInclude,
    });

    if (!session) {
      throw new NotFoundException(`Session ${sessionId} not found`);
    }

    return session;
  }
}
