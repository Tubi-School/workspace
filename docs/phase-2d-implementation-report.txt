================================================================================
D. AUTHORIZATION BEHAVIOR
================================================================================

Every controller is @UseGuards(JwtAuthGuard, RolesGuard) at the class
level, with @Roles('ADMIN') on every mutation and @Roles('ADMIN',
'TEACHER') on every read route — LEARNER is never named, so RolesGuard
denies it everywhere on these controllers (it only defaults to "any
authenticated user" when a route has NO @Roles() at all, which none of
these routes do). This is the first production use of the reusable
JwtAuthGuard/RolesGuard/@Roles infrastructure built in Phase 2C outside the
auth module itself, and the admin-rbac.http.spec.ts suite exercises it
end-to-end (real guards, real strategy, real signed tokens) rather than
only at the unit level.

================================================================================
E. VALIDATION / BUSINESS RULES
================================================================================

- GradeLevel / Subject: unique name, enforced via a pre-check (findUnique)
  on create and on update-with-name-change, returning 409 Conflict.

- AcademicTerm: startDate strictly before endDate, enforced by
  assertValidDateRange, applied on create and on update (re-validating
  against whichever date wasn't changed, so a partial update can't produce
  an invalid range by omission). timezone is optional in the DTO — when
  omitted, the value is left out of the Prisma `data` object entirely so
  the schema's own @default("Africa/Johannesburg") applies; when supplied,
  the caller's value is used.

- Course: all four references (subjectId, gradeLevelId, academicTermId,
  primaryTeacherId) are checked for existence via Promise.all before any
  write; every missing reference is collected and reported together in one
  response (assertReferencesExist), rather than failing on the first one
  found. UPDATED by the correction pass: a malformed UUID is rejected at
  the DTO layer with 400 Bad Request (via @IsUUID()) before this method
  ever runs; a syntactically valid UUID that resolves to no row is now
  reported with 404 Not Found, not 400 — the input was well-formed, the
  entity it points to simply doesn't exist.

- Deletion safety: GradeLevel/Subject/AcademicTerm refuse deletion (409
  Conflict) if any Course still references them (prisma.course.count);
  Course refuses deletion if any Session still references it
  (prisma.session.count). No cascade deletes were introduced, and no
  Prisma referential action (onDelete) was changed.

- DTOs: the global ValidationPipe (already configured in main.ts) with
  whitelist/forbidNonWhitelisted rejects unknown fields; @IsUUID() rejects
  malformed IDs; @MinLength(1) rejects empty names/titles.

Two issues were found and fixed during the original pass's verification,
both surfaced by tests, one a genuine production bug fix and one a
test-data fix — neither changed any product/business rule described in
section E, and neither was revisited by this correction pass:

1. AcademicTermsService.create was not declared `async`, so its
   synchronous assertValidDateRange throw bypassed Jest's `.rejects`
   matcher — a real inconsistency, since `update` on the same class was
   already `async` and behaved correctly. Fixed by adding `async` to
   `create`. This changes nothing about what the method validates or
   returns; it only makes a synchronous throw surface as a rejected
   Promise, consistent with the rest of the class and with how NestJS
   exception filters expect controller-bound methods to behave.
2. Two test files used hand-written placeholder UUIDs with an invalid
   variant nibble (e.g. "22222222-2222-2222-2222-222222222222"), which
   class-validator's @IsUUID() correctly rejected as malformed. Fixed by
   generating real UUIDs with `randomUUID()` in the test file. This was a
   test-data defect, not a validation-logic defect — @IsUUID() was working
   as intended.
