A. PHASE 2F SCOPE
================================================================================

Exact mission implemented (verbatim intent from the Phase 2F brief):

  Implement the real backend chain: Learner -> SubscriptionAccess ->
  SessionEntitlementSnapshot -> participation -> AttendanceRecord.

  Make TUBI capable of determining: which learner is entitled to which
  sessions, why they are entitled, whether they attended LIVE or RECORDED,
  whether they met the attendance threshold, whether they ultimately
  become PRESENT or ABSENT.

Concretely, this milestone implemented:
  A. LearnerProfile creation, wired atomically into public registration.
  B. SubscriptionAccess as an operational ADMIN-managed access grant.
  C. SessionEntitlementSnapshot generation at the entitlement point.
  D. Learner-facing session/attendance read API (identity from JWT only).
  E. Replacement-session entitlement inheritance across arbitrary chains.
  F. LiveAttendanceInterval ingestion + merged-coverage 50% LIVE engine.
  G. SessionRecording publication (ADMIN) + WatchedInterval ingestion
     (learner) + merged-coverage genuine-100% RECORDED engine.
  H. Effective attendance cutoff resolution, including
     AttendanceWindowException (session-wide and learner-specific).
  I. Idempotent absence finalization (PENDING -> ABSENT after cutoff).
  J. AttendanceRecord(PENDING) creation at entitlement time (not first
     participation).
  K. ADMIN (school-wide) and TEACHER (assignment-scoped) attendance reads.
  L. ADMIN-only manual attendance override with audit trail.

Deliberately excluded (per the brief's explicit "NOT IN PHASE 2F" list,
and confirmed still true after implementation):
  - Payment processor integration; no invoice/card/bank/payment-transaction
    ledger of any kind exists anywhere in the new code.
  - Zoom API integration and automatic webhook processing. LIVE interval
    ingestion is an internal HTTP endpoint a future adapter will call; no
    Zoom SDK/client exists.
  - Video hosting integration. SessionRecording.recordingUrl is stored and
    returned as an opaque string; nothing in this codebase uploads,
    transcodes, or streams video.
  - Frontend/UI. Backend only, as instructed.
  - HAPS, homework, notifications/email/SMS. Not referenced anywhere.

Assumptions used (each is a deliberate, documented engineering decision
made under the brief's "accelerated execution" instruction to resolve
non-semantic questions without stopping):
  1. [CORRECTED per external review Correction 1 — no longer an
     assumption] The session's frozen "entitlement point" (MIN(
     session.startTime, cancellationTime)) is now computed and supplied
     literally, not approximated by a button-press timestamp:
     SessionsService.markLive() (SCHEDULED -> LIVE) evaluates entitlement
     at `existing.startTime`, and SessionsService.cancel() evaluates it
     at `MIN(existing.startTime, new Date())` computed explicitly. The
     real system events (markLive/cancel being called) remain the
     triggers that decide WHEN evaluation runs — there is still no
     scheduler that fires exactly at startTime — but the VALUE passed to
     evaluateForSession is now the frozen entitlement point itself, not
     the trigger's own timestamp. For a session canceled directly from
     SCHEDULED (never having gone LIVE) whose scheduled start has not yet
     passed, this evaluates to the cancellation instant, matching the
     frozen rule. For a session canceled from LIVE, or canceled after its
     scheduled start has passed, this evaluates to session.startTime,
     matching what markLive would (or already did) evaluate — cancel()
     still calls evaluateForSession unconditionally in both cases, and
     evaluateForSession's upsert-based idempotency makes any redundant
     call a harmless no-op.
  2. LIVE interval ingestion (POST /admin/sessions/:id/live-intervals) is
     ADMIN-only in this phase, standing in for a future Zoom adapter or
     webhook processor — there is no distinct "system"/"service" role in
     the RBAC model yet.
  3. AttendanceWindowException precedence follows the frozen domain
     design's explicit stated order (learner-specific always wins over
     session-wide, regardless of which was granted more recently or has a
     later extendedCutoffAt) rather than a general "prefer the latest
     value" comparison — the frozen design document states an explicit
     order, which this implementation treats as authoritative over the
     brief's more general fallback wording.
  4. Multiple AttendanceWindowException rows may exist at the same scope
     over time (they are append-only, never updated in place); when more
     than one applies, the most recently created one is authoritative.
  5. A learner attempting to read a session/attendance record they are
     not entitled to receives 404 Not Found, never 403 Forbidden — so a
     caller cannot distinguish "this session does not exist" from "you
     have no relationship to it." (Internal, ADMIN-facing entitlement
     checks in the ingestion services still use 403, since an ADMIN
     already knows the session exists.)
  6. No DeliveryMode-based (LIVE_AND_RECORDED vs RECORDED_ONLY) filtering
     is applied to what a learner's session response exposes — see
     section M for why this was deferred rather than guessed at.

--- LearnersService (apps/api/src/learners/learners.service.ts) ---
Purpose: ADMIN read/management surface over LearnerProfile rows created by
public registration.
Public methods: findAll(), findOne(id), update(id, dto).
Business rules: passwordHash never selected (explicit Prisma `select` on
the `user` relation); no create endpoint (learners are created only via
AuthService.register); no delete endpoint (a LearnerProfile may already be
referenced by SubscriptionAccess/SessionEntitlementSnapshot/
AttendanceRecord/interval tables) — `isActive` on the underlying User row
is the supported deactivation path.
Transactions: none needed (single-table reads/updates plus one User
update).
Authorization: ADMIN-only, class-level `@Roles('ADMIN')` on
LearnersController.
Failure behavior: findOne/update throw NotFoundException (404) for a
missing id.

--- SubscriptionAccessService (apps/api/src/subscription-access/subscription-access.service.ts) ---
Purpose: operational surface for the SubscriptionAccess access-grant
model.
Public methods: create(dto), findAll(), findOne(id), update(id, dto),
revoke(id).
Business rules: learner must exist (404) and hold role LEARNER (409);
offering must exist (404); currentPeriodStart strictly before
currentPeriodEnd (400, `assertValidWindow`); for any grant whose resulting
status is ACTIVE, no overlapping ACTIVE grant may already exist for the
same (learnerId, offeringId) pair (409, `assertNoOverlappingActiveGrant`)
— checked on create and on update whenever the post-update status is
ACTIVE; non-ACTIVE grants (e.g. importing historical CANCELED/EXPIRED
records) skip the overlap check entirely; revoke() moves ACTIVE/PAST_DUE
to CANCELED (409 if already CANCELED/EXPIRED) — never a delete.
Transactions: none — the service relies on the pre-check plus the
downstream 404/409 semantics rather than a transactional write (a genuine
concurrent-duplicate-grant race is not fully closed by this
implementation — see section M).
Authorization: ADMIN-only for every method, including reads (class-level
`@Roles('ADMIN')`).
Failure behavior: NotFoundException (404) for missing learner/offering/
grant id; BadRequestException (400) for an invalid date window;
ConflictException (409) for an overlapping grant or an already-terminal
revoke target.

--- EntitlementService (apps/api/src/entitlements/entitlement.service.ts) ---
See section E for full behavioral documentation and section P for full
source. Public methods: evaluateForSession(sessionId, entitlementPoint),
inheritForReplacement(originalSessionId, replacementSessionId). Private:
writeEntitlementAndPendingAttendance (the shared idempotent-upsert
primitive both public methods funnel through). Transaction boundary: each
learner's (SessionEntitlementSnapshot upsert + AttendanceRecord upsert)
pair is one prisma.$transaction — the smallest unit that must be atomic;
the loop across learners is not itself one big transaction (each
learner's write is independently idempotent, so partial completion across

No direct HTTP authorization surface of its own.

--- AttendanceService (apps/api/src/attendance/attendance.service.ts) ---

================================================================================
E. SESSION ENTITLEMENT
================================================================================

Entitlement point [CORRECTED per external review Correction 1]: the
frozen entitlement point is now supplied literally rather than
approximated by a button-press timestamp.

  - Normal session: SessionsService.markLive() is the trigger, but the
    value passed is `existing.startTime` — the session's own scheduled
    start — not the moment the LIVE transition happens to be requested.
    `evaluateForSession(id, existing.startTime)`. Whether an ADMIN
    presses LIVE seven minutes late or twenty minutes early, entitlement
    is evaluated as of the session's scheduled start either way.

  - Cancellation before scheduled start: SessionsService.cancel()
    computes `entitlementPoint = cancellationTime.getTime() <
    existing.startTime.getTime() ? cancellationTime : existing.startTime`
    — i.e. `MIN(session.startTime, cancellationTime)` — and passes that
    computed value to evaluateForSession. When cancellation happens before
    the scheduled start, this evaluates to the cancellation instant.

  - Cancellation after scheduled start (including a session already
    LIVE): the same MIN expression evaluates to `existing.startTime`,
    matching what markLive would already have evaluated. cancel() still
    calls evaluateForSession unconditionally in this case (no branch
    distinguishes "already evaluated by markLive" from "not yet
    evaluated") — evaluateForSession's upsert-based idempotency (see
    below) makes this a harmless no-op when redundant.

This exactly matches the reviewer's required formula: entitlementPoint =
MIN(session.startTime, cancellationTime), where cancellationTime exists
only for a cancellation event, and the normal (non-canceled) case
resolves to session.startTime with no dependency on when markLive is
actually invoked.

Subscription eligibility: evaluateForSession resolves every Offering
covering the session's Course via OfferingCourse, then queries
SubscriptionAccess rows with status ACTIVE, offeringId in that set, and
currentPeriodStart <= entitlementPoint <= currentPeriodEnd. A learner
holding more than one qualifying grant still gets exactly one snapshot
(first-seen-wins, deterministic via Map insertion order).

Persistence: one SessionEntitlementSnapshot row per (sessionId,
learnerId), written via `upsert` with `update: {}` (a deliberate no-op) —
an existing snapshot's wasEntitled/subscriptionAccessId is never
overwritten once written, preserving it as historical truth. One
AttendanceRecord(PENDING) row is written in the same upsert step, same
guarantee.

Replacement-session inheritance: SessionsService.create(), when given
replacementForSessionId, validates the target is CANCELED (pre-existing
Phase 2E logic, unchanged) and then calls
`entitlementService.inheritForReplacement(target.id, newSession.id)`.
inheritForReplacement reads every wasEntitled snapshot on the original and
upserts a corresponding snapshot on the replacement, with
inheritedFromSnapshotId pointing at the exact snapshot it copied from —
never recalculated from current SubscriptionAccess state (the method
contains no query against subscriptionAccess at all).

Repeated replacement chains: because inheritForReplacement always reads
its immediate input session's own snapshots (not a globally-resolved
"original"), a chain Original -> Replacement A -> Replacement B produces
inheritedFromSnapshotId links where B's snapshot points at A's snapshot
and A's snapshot points at Original's snapshot — full ancestry is
recoverable by walking the chain. Verified directly by
entitlement.service.spec.ts's "preserves inheritance across a
multi-generation chain" test.

Protection against duplicate entitlement creation / idempotency &
concurrency: the unique constraint on SessionEntitlementSnapshot
(sessionId, learnerId) — pre-existing, frozen schema — is the actual
backstop; `upsert` is the application-level mechanism that makes repeated
or concurrent calls to evaluateForSession/inheritForReplacement for the
same session converge on the same row rather than erroring or duplicating.
Each learner's snapshot+attendance pair is written inside its own
`prisma.$transaction`, so a crash partway through a multi-learner
evaluation leaves only fully-consistent (snapshot, attendance-record)
pairs behind — never a snapshot with no matching attendance record or vice
versa.

single `prisma.$transaction` that first takes a transaction-scoped
Postgres advisory lock (`pg_advisory_xact_lock(hashtext(sessionId + ':' +
learnerId)::bigint)`) before running the create/reread/recompute/qualify
sequence. Two concurrent ingest() calls for the same (sessionId,
learnerId) pair are now fully serialized — the second call's transaction
blocks until the first commits (releasing the lock), so it always rereads
the first call's already-committed interval, and coverage is never
computed from a stale pre-insert snapshot. Concurrent calls for different
learners or different sessions never contend with each other (different
hash keys, no shared lock). See section P for the exact source of
`withLearnerSessionLock`.

Validation before write: session must exist (404); joinedAt strictly
before leftAt (400); learner must have an entitlement snapshot with
wasEntitled true (403, via AttendanceService.assertEntitled).

Cumulative interval calculation: after inserting the new row, ALL of that
learner's LiveAttendanceInterval rows for the session are re-read from the
database (never accumulated incrementally in memory across calls). Each
raw [joinedAt, leftAt] range is clipped to `[session.startTime,
session.endTime]` via `clipInterval` (open connections — `leftAt: null` —
are treated as open-until-now via `leftAt ?? new Date()`, though this
phase's DTO requires leftAt, so this branch exists for
defensiveness/forward-compatibility). Clipped ranges are then merged via
`mergeIntervals` (sorts by start, coalesces any overlap or adjacency) and
summed via `totalCoverage`.

Clipping to official session start/end: performed before merging, via
`clipInterval(rawInterval, { start: session.startTime, end:
session.endTime })` — a raw interval extending before startTime or after
endTime is truncated to the overlap only; an interval with no overlap at
all is dropped (`clipInterval` returns null, filtered out).

Overlap handling / reconnect handling / duplicates: because coverage is
always recomputed from the full merged set of ALL rows (not accumulated
per-call), two overlapping intervals collapse into their union
(mergeIntervals), so overlap never double-counts; two genuinely
disconnected intervals (a reconnect after a drop) both survive the merge
as separate spans and their durations both contribute to the sum — this is
what "temporary disconnects accumulate" means concretely. An exact
duplicate interval merges into the same single span as the original,
contributing no extra coverage.

Scheduled-duration calculation:
`session.endTime.getTime() - session.startTime.getTime()`, in
milliseconds.

>= 50% threshold: AttendanceService.qualifyLive is called with the
recomputed `coverageMs` and `scheduledDurationMs`; it returns immediately
(no-op) if `coverageMs < scheduledDurationMs * 0.5` — a strict
less-than, so coverage exactly equal to 50% passes through to
qualification (verified by test with an exact-boundary case).

When AttendanceRecord becomes PRESENT: qualifyLive calls
`markPresentIfPending(sessionId, learnerId, CompletionMode.LIVE,
qualifiedAt)`, where `qualifiedAt` is the `leftAt` timestamp of the
interval that was just ingested (i.e. the moment the learner's connection
that pushed cumulative coverage over the threshold ended). This is a
reasonable, documented choice for "timestamp when qualification was
achieved" given intervals are ingested as already-closed spans rather than
streamed live.

completionMode/completedAt behavior: `markPresentIfPending` first
resolves the effective cutoff (section H); if `qualifiedAt` is after that
cutoff, it returns without writing anything — the record stays PENDING
(to be finalized ABSENT later by section I's finalizer, exactly as if
nothing had happened). Otherwise it performs
`attendanceRecord.updateMany({ where: { sessionId, learnerId, status:
PENDING }, data: { status: PRESENT, completionMode: LIVE, completedAt:
qualifiedAt } })` — the `status: PENDING` guard in the WHERE clause is
what makes this safe under concurrent qualification attempts and
guarantees an already-PRESENT record is never re-written or downgraded.

Behavior after cutoff: covered above — a genuine qualification event
after the effective cutoff is silently discarded (the record is left
exactly as it was), never treated as attendance.

================================================================================
G. RECORDED ATTENDANCE ENGINE
================================================================================

Recording availability: RecordingService.publish (ADMIN-only) requires
the session to be ENDED; the resulting SessionRecording row (recordingUrl,
availableFrom, totalSeconds) is what WatchedIntervalService.ingest reads
via RecordingService.findForSession(sessionId), which throws
NotFoundException (404) if no recording has been published yet — so
progress cannot be ingested against a session with no recording at all.

Progress interval storage: WatchedIntervalService.ingest(sessionId,
learnerId, dto) — dto is `{ startSecond, endSecond }`, integers, no
learnerId field (always the value the controller resolved from the JWT).
Validation: startSecond strictly less than endSecond (400); learner
entitled (403, assertEntitled); recording exists (404, via
findForSession); interval falls within `[0, recording.totalSeconds]`
(400) — both a negative startSecond and an endSecond beyond the recording
duration are rejected. The interval is then inserted as a WatchedInterval
row scoped to `sessionRecordingId` + `learnerId`.

[CORRECTED per external review Correction 2] As with the LIVE engine, the
insert/reread/recompute/qualify sequence now runs inside
`withLearnerSessionLock`, under the same per-(sessionId, learnerId)
Postgres advisory lock, closing the same concurrency gap for RECORDED
ingestion.

Unique timeline coverage calculation: identical pattern to the LIVE
engine — after insert, ALL of that learner's WatchedInterval rows for this
recording are re-read, mapped to `{start: startSecond, end: endSecond}`,
merged via `mergeIntervals`, and summed via `totalCoverage`. No
client-supplied percentage is ever accepted (CreateWatchedIntervalDto has
no such field).

Overlap/duplicate handling: identical to LIVE — merge collapses
overlapping or duplicate ranges into their union, so they cannot inflate
the coverage sum.

Skipped portions: because coverage is the sum of the *merged* set, not
"latest timestamp reached," a client that jumps from second 120 to second
3480 (skipping the middle of an hour-long recording) produces two
disjoint merged intervals whose combined duration is nowhere near
totalSeconds — the brief's own example (0-15 + 30-60 of a 60-minute
recording = 45 minutes, not 100%) is a direct, named test case in
watched-interval.service.spec.ts.

Genuine 100% coverage requirement: AttendanceService.qualifyRecorded
returns (no-op) if `coverageSeconds < totalSeconds` — a strict less-than,
so anything short of the full integer-second duration fails; there is no
tolerance constant anywhere in this code, because WatchedInterval.
startSecond/endSecond are already whole integers (`Int` in the frozen
schema) — there is no sub-second rounding question to tolerate in the
first place, so no tolerance was introduced.

Cutoff enforcement: identical mechanism to LIVE — qualifyRecorded calls
the same `markPresentIfPending`, which resolves the effective cutoff and
discards (leaves PENDING) any qualification event timestamped after it.

AttendanceRecord transition to PRESENT / completionMode/completedAt: same
`markPresentIfPending` path as LIVE, with `CompletionMode.RECORDED` and
`qualifiedAt = new Date()` (the moment the ingest call that pushed
coverage to 100% was processed) as the timestamp, guarded by the same
`status: PENDING` compare-and-swap update.

================================================================================
H. ATTENDANCE CUTOFF AND ABSENCE
================================================================================

Africa/Johannesburg academic-day handling and the normal 23:59 cutoff:
unchanged from Phase 2E — `Session.attendanceCutoffAt` is computed at
session-creation/update time by `computeAttendanceCutoffAtUtc` (apps/api/
src/sessions/academic-timezone.util.ts, not modified in Phase 2F) and
stored as a plain UTC DateTime column. Phase 2F reads this column as the
fallback tier of `AttendanceService.getEffectiveCutoff` — it does not
recompute or reinterpret it.

Session-wide exceptions: an AttendanceWindowException row with `learnerId:
null`, created via WindowExceptionService.create (ADMIN-only,
`POST /admin/sessions/:id/window-exceptions` with no learnerId in the
body).

Learner-specific exceptions: the same entity/endpoint with `learnerId` set
to a specific LearnerProfile id (validated to exist, 404 otherwise).

Precedence: `AttendanceService.getEffectiveCutoff(sessionId, learnerId)`
checks, in this exact order: (1) the most recent learner-specific
exception for this (session, learner) pair — if found, its
`extendedCutoffAt` is returned immediately, full stop; (2) else the most
recent session-wide exception for this session — if found, its
`extendedCutoffAt` is returned; (3) else `session.attendanceCutoffAt`.
This is a strict override hierarchy, not a "pick whichever value is
chronologically latest" comparison — verified directly by a test where the
session-wide grant's extendedCutoffAt is chronologically later than the
learner-specific one, and the learner-specific one still wins.

How PENDING becomes ABSENT: `AttendanceService.finalizeDueRecords()`
reads every AttendanceRecord currently `status: PENDING`, computes each
one's effective cutoff, and for any where `now > effectiveCutoff`,
executes `attendanceRecord.updateMany({ where: { sessionId, learnerId,
status: PENDING }, data: { status: ABSENT, completionMode: null,
completedAt: null } })`.

Confirmation that ABSENT has completionMode = null and completedAt =
null: yes — both are explicitly set to `null` in the same `updateMany`
call that sets `status: ABSENT`; there is no code path anywhere that sets
ABSENT with either field populated.

Idempotency of finalization: the `status: PENDING` guard in every
`updateMany`'s WHERE clause means a record already moved off PENDING (by
this same finalizer on a prior run, by a concurrent run, or by having
qualified PRESENT in the interim) contributes 0 to the affected-row count
and is never touched again. `finalizeDueRecords` is exposed as
`POST /admin/attendance/finalize` (ADMIN-only) — a plain, repeatable,
side-effect-safe call, with no scheduler wired to it yet (deliberately, per
the brief).

================================================================================
J. AUTHORIZATION
================================================================================

ADMIN can:
  - Read and manage LearnerProfiles (list/get/deactivate; never delete).
  - Create/read/update/revoke SubscriptionAccess grants.
  - Ingest LIVE intervals on behalf of the (future) Zoom adapter.
  - Publish recordings.
  - Create and list AttendanceWindowException rows, session-wide or
    learner-specific.
  - Read attendance school-wide, by session or by learner, including
    coverage summaries.
  - Perform manual attendance overrides (with mandatory reason and
    automatic audit attribution).
  - Trigger absence finalization on demand.
  - Everything TEACHER/LEARNER can do is a strict subset of ADMIN's
    access in this milestone — there is no ADMIN-exclusive learner-portal
    or teacher-portal route ADMIN is blocked from; ADMIN simply has its
    own separate, broader `/admin/*` surface instead.

TEACHER can:
  - Read attendance for a session ONLY if their own TeacherProfile has a
    SessionTeacher row for that session, in ANY of the three roles
    (PRIMARY, ASSISTANT, or SUBSTITUTE) — `assertTeacherAssignedToSession`
    does not distinguish between the three roles for this read-scoping
    check; all three grant the same attendance-read visibility for that
    session. A TEACHER with no SessionTeacher row for a session gets 403.
  - Cannot mutate anything in this module: no TEACHER route exists for
    subscription access, window exceptions, recording publication, LIVE
    ingestion, or override — TEACHER-role requests to any ADMIN-only route
    are rejected by RolesGuard before reaching a controller method (403).
  - No PRIMARY/ASSISTANT/SUBSTITUTE distinction is implemented for
    authorization purposes in Phase 2F beyond "assigned in any role
    grants the same read access" — the brief's staffing-role distinctions
    (from Phase 2E) are not further refined here; Phase 2F does not
    introduce any new role-specific permission tied to PRIMARY vs
    ASSISTANT vs SUBSTITUTE.

LEARNER can:
  - List and read only sessions they hold a `wasEntitled: true`
    SessionEntitlementSnapshot for; anything else reads as 404.
  - Read only their own AttendanceRecord and coverage summary, for an
    entitled session; the learnerId used is always resolved from the JWT,
    never accepted from the client.
  - Submit their own WatchedInterval progress for an entitled session with
    a published recording; cannot submit on behalf of another learner
    (no learnerId field exists in the DTO to do so).
  - Cannot create/read AttendanceWindowException rows, cannot ingest LIVE
    intervals, cannot publish recordings, cannot perform overrides, cannot
    trigger finalization, cannot read another learner's data in any form.

   role in the RBAC model yet; when real Zoom integration arrives it will
   very likely need its own authentication mechanism (a service
   credential or webhook signature) rather than a human ADMIN's JWT.

2. No DeliveryMode-based (LIVE_AND_RECORDED vs RECORDED_ONLY) gating
   exists on what a learner's session response exposes — a learner
   entitled only to a RECORDED_ONLY offering currently still sees
   `liveMeetingUrl` in `GET /learner/sessions`, identical to a
   LIVE_AND_RECORDED subscriber. Deferred deliberately: correct behavior
   depends on a product decision about gating per-Offering vs
   per-SubscriptionAccess when a learner holds multiple concurrent
   grants, which felt safer to defer than to guess.

3. LIVE interval ingestion requires both `joinedAt` and `leftAt` in one
   call (a completed interval) — there is no "open connection" streaming
   ingestion path (join now, close later) in this milestone, even though
   the schema's `leftAt` column is nullable specifically to support that.
   `LiveAttendanceInterval.leftAt` being null is handled defensively in
   coverage calculation (`leftAt ?? new Date()`) but no code path
   currently writes a null `leftAt`. A future Zoom adapter integration
   will need to decide whether to report intervals only after they close,
   or to extend this ingestion to support open/streaming intervals.

4. SubscriptionAccessService's overlap check (`assertNoOverlappingActiveGrant`)
   is a pre-check, not enforced by a database constraint or a
   transaction — a genuine concurrent race (two admins granting
   overlapping ACTIVE access to the same learner+offering at the same
   instant) is not fully closed the way the email-uniqueness race in
   AuthService/TeachersService is (which additionally catches the
   database's own P2002). This is a real, if narrow, gap: the frozen
   schema has no unique constraint that could close it structurally
   (SubscriptionAccess has no natural composite-uniqueness column set
   given arbitrary date ranges), so closing it fully would require either
   a serializable transaction/advisory lock or a generated exclusion
   constraint — out of scope for this milestone, flagged for follow-up.

5. `finalizeDueRecords()` has no production scheduler wired to it, per
   the brief's explicit instruction not to build that integration now. It
   is a plain, idempotent, ADMIN-callable HTTP endpoint

/**
 * Generic numeric interval merge/coverage math, shared by the LIVE
 * (LiveAttendanceInterval, millisecond epoch values) and RECORDED
 * (WatchedInterval, integer second values) coverage engines. Neither
 * engine trusts a client-supplied percentage — both derive coverage from
 * the actual union of reported ranges, so overlapping or duplicate
 * intervals can never inflate the total, and a skipped span always leaves
 * a genuine gap.
 */
export interface NumericInterval {
  start: number;
  end: number;
}

/** Sorts and merges overlapping/adjacent intervals into the minimal
 * non-overlapping set representing their union. */
export function mergeIntervals(intervals: NumericInterval[]): NumericInterval[] {
  if (intervals.length === 0) {
    return [];
  }

  const sorted = [...intervals].sort((a, b) => a.start - b.start);
  const merged: NumericInterval[] = [{ ...sorted[0]! }];

  for (let i = 1; i < sorted.length; i += 1) {
    const current = sorted[i]!;
    const last = merged[merged.length - 1]!;

    if (current.start <= last.end) {
      last.end = Math.max(last.end, current.end);
    } else {
      merged.push({ ...current });
    }
  }

  return merged;
}

/** Sum of durations across (already-merged, non-overlapping) intervals. */
export function totalCoverage(intervals: NumericInterval[]): number {
  return intervals.reduce((sum, interval) => sum + (interval.end - interval.start), 0);
}

/** Clips `interval` to `bounds`, returning null if there is no overlap at
 * all (rather than a zero/negative-length interval). */
export function clipInterval(
  interval: NumericInterval,
  bounds: NumericInterval,
): NumericInterval | null {
  const start = Math.max(interval.start, bounds.start);
  const end = Math.min(interval.end, bounds.end);

  return end > start ? { start, end } : null;
}

import { Injectable } from '@nestjs/common';

import {
  AttendanceStatus,
  SubscriptionStatus,
  type SubscriptionAccess,
} from '../generated/prisma/client.js';
import { PrismaService } from '../prisma/prisma.service.js';

/**
 * The frozen entitlement engine (docs/phase-2a-final-domain-design.txt,
 * sections I and J).
 *
 * Every operation here is idempotent by construction — `upsert` on the
 * unique (sessionId, learnerId) constraints already present on
 * SessionEntitlementSnapshot and AttendanceRecord — so calling it more than
 * once for the same session (a retry, a race between two admins, a future
 * scheduler firing twice) never creates a duplicate row or changes an
 * already-recorded entitlement decision. A snapshot is historical truth:
 * once written, this service never overwrites `wasEntitled` or
 * `subscriptionAccessId` on an existing row — `update: {}` in every upsert
 * below is a deliberate no-op, not an oversight.
 */
@Injectable()
export class EntitlementService {
  constructor(private readonly prisma: PrismaService) {}

  /**
   * Evaluates "normal" entitlement for a session at `entitlementPoint` —
   * the moment the frozen design calls the session's entitlement point
   * (MIN(session.startTime, session.canceledAt), approximated here by the
   * real system event that triggers evaluation: the session going LIVE, or
   * being canceled before it ever did — see SessionsService.markLive and
   * SessionsService.cancel).
   *
   * For every learner holding an ACTIVE SubscriptionAccess, for an
   * Offering that covers this session's Course, whose period covers
   * `entitlementPoint`, this writes a SessionEntitlementSnapshot
   * (wasEntitled: true) and idempotently ensures a PENDING AttendanceRecord
   * exists — so a learner who never interacts with the session at all can
   * still later be finalized ABSENT (Part J of the Phase 2F brief).
   */
  async evaluateForSession(sessionId: string, entitlementPoint: Date): Promise<void> {
    const session = await this.prisma.session.findUniqueOrThrow({
      where: { id: sessionId },
      select: { courseId: true },
    });

    const offeringLinks = await this.prisma.offeringCourse.findMany({
      where: { courseId: session.courseId },
      select: { offeringId: true },
    });
    const offeringIds = offeringLinks.map((link) => link.offeringId);

    if (offeringIds.length === 0) {
      return;
    }

    const grants = await this.prisma.subscriptionAccess.findMany({
      where: {
        offeringId: { in: offeringIds },
        status: SubscriptionStatus.ACTIVE,
        currentPeriodStart: { lte: entitlementPoint },
        currentPeriodEnd: { gte: entitlementPoint },
      },
    });

    // A learner may hold more than one qualifying grant (e.g. two
    // overlapping offerings covering the same course); one snapshot per
    // learner is still correct — pick the first deterministically.
    const grantByLearner = new Map<string, SubscriptionAccess>();
    for (const grant of grants) {
      if (!grantByLearner.has(grant.learnerId)) {
        grantByLearner.set(grant.learnerId, grant);
      }
    }

    for (const [learnerId, grant] of grantByLearner) {
      await this.writeEntitlementAndPendingAttendance(sessionId, learnerId, {
        subscriptionAccessId: grant.id,
        snapshotAt: entitlementPoint,
        inheritedFromSnapshotId: null,
      });
    }
  }

  /**
   * Replacement-session entitlement inheritance (frozen design section J).
   *
   * For every learner entitled to the canceled `originalSessionId`, copies
   * that entitlement onto `replacementSessionId` — never recalculated from
   * today's subscription state — with `inheritedFromSnapshotId` pointing at
   * the immediate predecessor's snapshot. This is what lets a multi-hop
   * replacement chain (Original -> Replacement A -> Replacement B) stay
   * traceable: each snapshot links only to its direct parent, and the full
   * ancestry is recovered by walking the chain.
   */
  async inheritForReplacement(
    originalSessionId: string,
    replacementSessionId: string,
  ): Promise<void> {
    const originalSnapshots = await this.prisma.sessionEntitlementSnapshot.findMany({
      where: { sessionId: originalSessionId, wasEntitled: true },
    });

    for (const snapshot of originalSnapshots) {
      await this.writeEntitlementAndPendingAttendance(replacementSessionId, snapshot.learnerId, {
        subscriptionAccessId: snapshot.subscriptionAccessId,
        snapshotAt: new Date(),
        inheritedFromSnapshotId: snapshot.id,
      });
    }
  }

  private async writeEntitlementAndPendingAttendance(
    sessionId: string,
    learnerId: string,
    fields: {
      subscriptionAccessId: string | null;
      snapshotAt: Date;
      inheritedFromSnapshotId: string | null;
    },
  ): Promise<void> {
    await this.prisma.$transaction(async (tx) => {
      await tx.sessionEntitlementSnapshot.upsert({
        where: { sessionId_learnerId: { sessionId, learnerId } },
        update: {},
        create: {
          sessionId,
          learnerId,
          wasEntitled: true,
          subscriptionAccessId: fields.subscriptionAccessId,
          snapshotAt: fields.snapshotAt,
          inheritedFromSnapshotId: fields.inheritedFromSnapshotId,
        },
      });

      await tx.attendanceRecord.upsert({
        where: { sessionId_learnerId: { sessionId, learnerId } },
        update: {},
        create: { sessionId, learnerId, status: AttendanceStatus.PENDING },
      });
    });
  }
}

  /**
   * Resolves the deadline that actually applies to one learner on one
   * session: a learner-specific AttendanceWindowException, if one exists,
   * always wins outright over a session-wide one — this is the explicit
   * precedence the frozen design states (section G/K), not a "pick the
   * latest of all applicable values" comparison. Falls back to the
   * session's own normal cutoff when no exception exists. When more than
   * one exception exists at the same scope (a corrected/superseding grant),
   * the most recently created one is authoritative — exceptions are an
   * append-only audit log, never edited in place.
   */
  async getEffectiveCutoff(
    sessionId: string,
    learnerId: string,
    db: Db = this.prisma,
  ): Promise<Date> {
    const session = await db.session.findUniqueOrThrow({
      where: { id: sessionId },
      select: { attendanceCutoffAt: true },
    });

    const learnerException = await db.attendanceWindowException.findFirst({
      where: { sessionId, learnerId },
      orderBy: { createdAt: 'desc' },
    });
    if (learnerException) {
      return learnerException.extendedCutoffAt;
    }

    const sessionWideException = await db.attendanceWindowException.findFirst({
      where: { sessionId, learnerId: null },
      orderBy: { createdAt: 'desc' },
    });
    if (sessionWideException) {
      return sessionWideException.extendedCutoffAt;
    }

    return session.attendanceCutoffAt;
  }

  async qualifyLive(
    sessionId: string,
    learnerId: string,
    coverageMs: number,
    scheduledDurationMs: number,
    qualifiedAt: Date,
    db: Db = this.prisma,
  ): Promise<void> {
    if (coverageMs < scheduledDurationMs * 0.5) {
      return;
    }
    await this.markPresentIfPending(sessionId, learnerId, CompletionMode.LIVE, qualifiedAt, db);
  }

  async qualifyRecorded(
    sessionId: string,
    learnerId: string,
    coverageSeconds: number,
    totalSeconds: number,
    qualifiedAt: Date,
    db: Db = this.prisma,
  ): Promise<void> {
    if (coverageSeconds < totalSeconds) {
      return;
    }
    await this.markPresentIfPending(sessionId, learnerId, CompletionMode.RECORDED, qualifiedAt, db);
  }

  private async markPresentIfPending(
    sessionId: string,
    learnerId: string,
    mode: CompletionMode,
    qualifiedAt: Date,
    db: Db = this.prisma,
  ): Promise<void> {
    const effectiveCutoff = await this.getEffectiveCutoff(sessionId, learnerId, db);

    if (qualifiedAt.getTime() > effectiveCutoff.getTime()) {
      // Genuine completion, but after the deadline: not ordinary
      // attendance. The record is left PENDING; the finalizer (Part I)
      // will move it to ABSENT once its cutoff has passed, exactly as if
      // nothing had been watched at all.
      return;
    }

    // `updateMany` with a `status: PENDING` guard, rather than a plain
    // `update`, is what makes this safe under concurrent qualification
    // attempts (e.g. two ingested intervals racing) and guarantees PRESENT
    // is never downgraded or re-timestamped once set. `db` is the caller's
    // active transaction when invoked from interval ingestion (see
    // learner-session-lock.util.ts above), so this write participates in
    // the same advisory-locked transaction as the interval insert/reread.
    await db.attendanceRecord.updateMany({
      where: { sessionId, learnerId, status: AttendanceStatus.PENDING },
      data: { status: AttendanceStatus.PRESENT, completionMode: mode, completedAt: qualifiedAt },
    });
  }

  /**
   * Moves every still-PENDING AttendanceRecord whose effective cutoff has
   * passed to ABSENT. Idempotent and safe to call repeatedly or
   * concurrently: the `status: PENDING` guard on the update means a record
   * already finalized (by this call or a concurrent one) or already
   * PRESENT is never touched again.
   */
  async finalizeDueRecords(): Promise<{ finalizedCount: number }> {
    const duePending = await this.prisma.attendanceRecord.findMany({
      where: { status: AttendanceStatus.PENDING },
      select: { sessionId: true, learnerId: true },
    });

    const now = new Date();
    let finalizedCount = 0;

    for (const { sessionId, learnerId } of duePending) {
      const effectiveCutoff = await this.getEffectiveCutoff(sessionId, learnerId);

      if (now.getTime() > effectiveCutoff.getTime()) {
        const result = await this.prisma.attendanceRecord.updateMany({
          where: { sessionId, learnerId, status: AttendanceStatus.PENDING },
          data: { status: AttendanceStatus.ABSENT, completionMode: null, completedAt: null },
        });
        finalizedCount += result.count;
      }
    }

    return { finalizedCount };
  }

import { Prisma } from '../generated/prisma/client.js';
import { PrismaService } from '../prisma/prisma.service.js';

/**
 * Runs `fn` inside a Postgres transaction that first takes a
 * transaction-scoped advisory lock keyed by (sessionId, learnerId).
 *
 * This is the smallest robust fix for the interval-ingestion concurrency
 * gap identified in the Phase 2F external review: without it, two
 * concurrent ingest() calls for the same learner+session could each read
 * the prior interval set before the other's just-inserted row committed,
 * silently under-counting coverage. `pg_advisory_xact_lock` serializes
 * only requests that collide on the same (sessionId, learnerId) pair —
 * unrelated learners and sessions never contend — and the lock is released
 * automatically when the transaction commits or rolls back, so no manual
 * unlock/cleanup path is needed. No schema change is required: advisory
 * locks are a session-level Postgres primitive, not a table.
 *
 * `hashtext(...)::bigint` folds the composite key into the single bigint
 * `pg_advisory_xact_lock` takes. A hash collision between two different
 * (sessionId, learnerId) pairs would only ever cause extra, harmless
 * serialization (never incorrect data), so no collision-avoidance beyond
 * hashtext's own distribution is needed here.
 */
export async function withLearnerSessionLock<T>(
  prisma: PrismaService,
  sessionId: string,
  learnerId: string,
  fn: (tx: Prisma.TransactionClient) => Promise<T>,
): Promise<T> {
  const lockKey = `${sessionId}:${learnerId}`;

  return prisma.$transaction(async (tx) => {
    await tx.$queryRaw`SELECT pg_advisory_xact_lock(hashtext(${lockKey})::bigint)`;
    return fn(tx);
  });
}

import { BadRequestException, Injectable, NotFoundException } from '@nestjs/common';

import { PrismaService } from '../prisma/prisma.service.js';
import { AttendanceService } from './attendance.service.js';
import type { CreateLiveIntervalDto } from './dto/create-live-interval.dto.js';
import {
  clipInterval,
  mergeIntervals,
  totalCoverage,
  type NumericInterval,
} from './interval-merge.util.js';
import { withLearnerSessionLock } from './learner-session-lock.util.js';

/**
 * Internal ingestion for LIVE participation — the seam a future Zoom
 * adapter attaches to (Part E of the Phase 2F brief). Every ingested
 * interval is clipped to the session's scheduled window before it is ever
 * summed, so time outside [startTime, endTime] never counts, and
 * overlapping/duplicate intervals never double-count because coverage is
 * always recomputed from the full merged set, not accumulated
 * incrementally.
 */
@Injectable()
export class LiveAttendanceIntervalService {
  constructor(
    private readonly prisma: PrismaService,
    private readonly attendanceService: AttendanceService,
  ) {}

  async ingest(sessionId: string, dto: CreateLiveIntervalDto): Promise<void> {
    const session = await this.prisma.session.findUnique({ where: { id: sessionId } });

    if (!session) {
      throw new NotFoundException(`Session ${sessionId} not found`);
    }

    const joinedAt = new Date(dto.joinedAt);
    const leftAt = new Date(dto.leftAt);

    if (joinedAt.getTime() >= leftAt.getTime()) {
      throw new BadRequestException('joinedAt must be strictly before leftAt');
    }

    await this.attendanceService.assertEntitled(sessionId, dto.learnerId);

    // The insert-reread-recompute-qualify sequence below must behave as one
    // consistent operation under concurrent submissions for the same
    // (sessionId, learnerId) pair — otherwise two racing ingest() calls
    // could each read the coverage set before the other's row is visible,
    // silently losing one interval's contribution to the merged coverage
    // total. A Postgres session-scoped advisory lock, held for the
    // duration of one `$transaction`, serializes concurrent ingestion for
    // the same learner+session without requiring any schema change:
    // requests for different learners/sessions never contend, and a
    // request for the same pair simply waits its turn. See
    // learner-session-lock.util.ts for the exact mechanism.
    await withLearnerSessionLock(this.prisma, sessionId, dto.learnerId, async (tx) => {
      await tx.liveAttendanceInterval.create({
        data: { sessionId, learnerId: dto.learnerId, joinedAt, leftAt },
      });

      const allIntervals = await tx.liveAttendanceInterval.findMany({
        where: { sessionId, learnerId: dto.learnerId },
      });

      const bounds: NumericInterval = {
        start: session.startTime.getTime(),
        end: session.endTime.getTime(),
      };
      const clipped = allIntervals
        .map((interval) =>
          clipInterval(
            { start: interval.joinedAt.getTime(), end: (interval.leftAt ?? new Date()).getTime() },
            bounds,
          ),
        )
        .filter((interval): interval is NumericInterval => interval !== null);

      const coverageMs = totalCoverage(mergeIntervals(clipped));
      const scheduledDurationMs = session.endTime.getTime() - session.startTime.getTime();

      await this.attendanceService.qualifyLive(
        sessionId,
        dto.learnerId,
        coverageMs,
        scheduledDurationMs,
        leftAt,
        tx,
      );
    });
  }
}

import { BadRequestException, Injectable } from '@nestjs/common';

import { PrismaService } from '../prisma/prisma.service.js';
import { AttendanceService } from './attendance.service.js';
import type { CreateWatchedIntervalDto } from './dto/create-watched-interval.dto.js';

import { withLearnerSessionLock } from './learner-session-lock.util.js';

/**
 * Learner-facing RECORDED playback ingestion (Part G). Never accepts a
 * client-reported percentage — only raw played ranges, which are merged
 * against everything previously reported before coverage is recomputed
 * from scratch, so skipping ahead always leaves the skipped span
 * genuinely uncovered and re-watching a span never inflates the total.
 */
@Injectable()
export class WatchedIntervalService {
  constructor(
    private readonly prisma: PrismaService,
    private readonly attendanceService: AttendanceService,
    private readonly recordingService: RecordingService,
  ) {}

  async ingest(sessionId: string, learnerId: string, dto: CreateWatchedIntervalDto): Promise<void> {
    if (dto.startSecond >= dto.endSecond) {
      throw new BadRequestException('startSecond must be strictly before endSecond');
    }

    await this.attendanceService.assertEntitled(sessionId, learnerId);

    const recording = await this.recordingService.findForSession(sessionId);

    if (dto.startSecond < 0 || dto.endSecond > recording.totalSeconds) {
      throw new BadRequestException(
        `Interval [${dto.startSecond}, ${dto.endSecond}] falls outside the recording's duration (0-${recording.totalSeconds})`,
      );
    }

    // See learner-session-lock.util.ts: serializes the create-reread-
    // recompute-qualify sequence for this (sessionId, learnerId) pair so
    // concurrent submissions can never lose coverage.
    await withLearnerSessionLock(this.prisma, sessionId, learnerId, async (tx) => {
      await tx.watchedInterval.create({
        data: {
          sessionRecordingId: recording.id,
          learnerId,
          startSecond: dto.startSecond,
          endSecond: dto.endSecond,
        },
      });

      const allIntervals = await tx.watchedInterval.findMany({
        where: { sessionRecordingId: recording.id, learnerId },
      });

      const coverageSeconds = totalCoverage(
        mergeIntervals(
          allIntervals.map((interval) => ({
            start: interval.startSecond,
            end: interval.endSecond,
          })),
        ),
      );

      await this.attendanceService.qualifyRecorded(
        sessionId,
        learnerId,
        coverageSeconds,
        recording.totalSeconds,
        new Date(),
        tx,
      );
    });
  }
}

import { Injectable, NotFoundException } from '@nestjs/common';

import type { AttendanceWindowException } from '../generated/prisma/client.js';
import { PrismaService } from '../prisma/prisma.service.js';
import type { CreateWindowExceptionDto } from './dto/create-window-exception.dto.js';

/** ADMIN-only, auditable extensions to a session's normal attendance
 * cutoff — session-wide (learnerId omitted) or learner-specific. Every
 * grant is append-only; see AttendanceService.getEffectiveCutoff for how
 * precedence and "most recent wins within a scope" are resolved. */
@Injectable()
export class WindowExceptionService {
  constructor(private readonly prisma: PrismaService) {}

  async create(
    sessionId: string,
    dto: CreateWindowExceptionDto,
    grantedByUserId: string,
  ): Promise<AttendanceWindowException> {
    const session = await this.prisma.session.findUnique({ where: { id: sessionId } });

    if (!session) {
      throw new NotFoundException(`Session ${sessionId} not found`);
    }

    if (dto.learnerId !== undefined) {
      const learner = await this.prisma.learnerProfile.findUnique({ where: { id: dto.learnerId } });

      if (!learner) {
        throw new NotFoundException(`Learner ${dto.learnerId} not found`);
      }
    }

    return this.prisma.attendanceWindowException.create({
      data: {
        sessionId,
        learnerId: dto.learnerId ?? null,
        reason: dto.reason,
        extendedCutoffAt: new Date(dto.extendedCutoffAt),
        grantedByUserId,
        note: dto.note,
      },
    });
  }

  findForSession(sessionId: string): Promise<AttendanceWindowException[]> {
    return this.prisma.attendanceWindowException.findMany({
      where: { sessionId },
      orderBy: { createdAt: 'desc' },
    });
  }
}
