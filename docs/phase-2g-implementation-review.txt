D. DELIVERYMODE ENFORCEMENT
================================================================================

The frozen `Offering.deliveryMode` enum has exactly two values:
`LIVE_AND_RECORDED` and `RECORDED_ONLY` (docs/phase-2a-final-domain-design.txt,
section D). Prior to Phase 2G, nothing in the codebase read this field at
attendance-ingestion time — a learner entitled only through a
RECORDED_ONLY offering could still submit LIVE participation and a
learner-portal read always exposed `liveMeetingUrl` regardless of
entitlement.

Mechanism (see section W for full source) [CORRECTED per external review
Correction 3 — fails closed]:
  - `AttendanceService.resolvePermittedDeliveryMode(sessionId, learnerId,
    db)` reads the learner's own SessionEntitlementSnapshot for this
    session, joined to `subscriptionAccess.offering`, and returns that
    offering's `deliveryMode` — never the learner's current live
    subscription, so a later plan change cannot retroactively alter what
    a session already entitled a learner to (the same "historical truth"
    principle SessionEntitlementSnapshot already embodies for
    entitlement itself). Return type is `DeliveryMode | null`: a snapshot
    with no linked subscriptionAccess/offering now resolves to `null`,
    never a default `LIVE_AND_RECORDED` — entitlement-origin data that is
    missing or inconsistent must never be silently upgraded to a
    permissive authorization outcome.
  - `AttendanceService.assertLiveDeliveryModeAllowed(sessionId,
    learnerId, db)` now requires AFFIRMATIVE evidence: it throws
    `ForbiddenException` (403) whenever the resolved mode is anything
    OTHER than `LIVE_AND_RECORDED` — one condition,
    `deliveryMode !== DeliveryMode.LIVE_AND_RECORDED`, covering both
    `RECORDED_ONLY` and `null` identically. Previously this only checked
    for `RECORDED_ONLY` specifically, which is what let a `null`
    (unresolvable) case fall through unguarded before Correction 3.
  - `LiveAttendanceIntervalService.ingest()` calls this immediately after
    `assertEntitled`, before any interval is written — unchanged call
    site, corrected callee behavior.
  - `WatchedIntervalService.ingest()` does NOT need a symmetric check:
    both enum values include recorded access, so there is no DeliveryMode
    value that could make a RECORDED submission invalid — see
    Assumptions in section A.
  - `LearnerPortalService`'s `redactLiveAccess` helper now takes
    `deliveryMode: DeliveryMode | null` and exposes `liveMeetingUrl` only
    when `deliveryMode === DeliveryMode.LIVE_AND_RECORDED` — redacting it
    to `''` for both `RECORDED_ONLY` and `null` alike. This is the same
    Session row for every caller — no second Session is ever created for
    a redacted learner, exactly as instructed.

Tests (15 total across 3 files, +3 from the pre-correction 12):
live-attendance.service.spec.ts (reject RECORDED_ONLY, allow
LIVE_AND_RECORDED, the CANCELED-session guard, and — new —
FAILS CLOSED: reject when subscriptionAccess is null);
learner-portal.service.spec.ts (redact for RECORDED_ONLY, pass through

.toHaveBeenCalled()` in the single-session case).

E. SUBSCRIPTION CONCURRENCY SOLUTION
================================================================================

Problem (Phase 2F review, section M, item 4): `assertNoOverlappingActiveGrant`
was a plain pre-check before `create`/`update` — two simultaneous requests
for the same (learnerId, offeringId) pair could each pass the check before
either transaction committed, producing two conflicting ACTIVE grants.

Fix: the smallest robust PostgreSQL-compatible mechanism, matching the
pattern already established for interval ingestion in Phase 2F —
`pg_advisory_xact_lock`, generalized into a new shared helper
(`common/pg-advisory-lock.util.ts`) so both use sites share one
implementation rather than duplicating the transaction-plus-raw-SQL
pattern. `SubscriptionAccessService.create()`/`update()` now run the
overlap check and the write inside
`withAdvisoryLock(prisma, `subscription-access:${learnerId}:${offeringId}`,
...)` — a single Postgres transaction that first takes a lock keyed by
exactly the (learnerId, offeringId) pair being written. Two concurrent
requests for the SAME pair are fully serialized (the second's transaction
blocks until the first commits and releases the lock, so it always
re-checks against the first's already-committed row); requests for
different learners or different offerings never contend with each other,
so legitimate unrelated grants remain fully concurrent. No schema change
was made or needed — `assertNoOverlappingActiveGrant`'s query and the
409 it raises are byte-for-byte unchanged; only the transaction/locking
wrapper around it changed.

Tests added (2): one asserting the overlap check and the create are both
inside exactly one `$transaction`/`$queryRaw` pair, in the correct order;
one demonstrating a different (learnerId, offeringId) pair succeeds
independently. Combined with the 6 pre-existing `create`/`revoke` tests,
the full concurrency-and-correctness picture (overlap detection, non-
overlap success, invalid window, missing learner/offering, non-ACTIVE
grants skip the check, revoke semantics) remains covered.

F. ATTENDANCE SCHEDULER/FINALIZER
================================================================================

`AttendanceService.finalizeDueRecords()` (built in Phase 2F) is unchanged
— still idempotent via `updateMany` guarded by `status: PENDING` in the
WHERE clause, still respects session-wide and learner-specific
AttendanceWindowException precedence via `getEffectiveCutoff`, still sets
`completionMode: null, completedAt: null` on every ABSENT it writes, and
still never touches an already-PRESENT record (the WHERE clause excludes
it). None of this logic was modified.

What Phase 2G adds is the trigger: `AttendanceFinalizerScheduler`
(`@nestjs/schedule`), registered via `ScheduleModule.forRoot()` in
AppModule, calling `finalizeDueRecords()` on a fixed
`@Cron(CronExpression.EVERY_5_MINUTES)` schedule — no administrator
action required for normal operation. The existing
`POST /admin/attendance/finalize` endpoint is unchanged and kept
specifically for operational recovery (e.g. after an extended outage),
per the brief's explicit instruction.

Interval choice: every 5 minutes. Documented directly in the scheduler's
own source comment (section W) — the frozen cutoff granularity is a fixed
clock instant (23:59 Africa/Johannesburg, or an explicit
AttendanceWindowException timestamp) with no sub-minute precision
requirement anywhere in the frozen domain design, so finalizing up to ~5
minutes after the exact cutoff changes no founder-defined semantics.

Multi-replica safety: not a new concern this scheduler introduces —
`finalizeDueRecords`'s idempotency (pre-existing) is exactly what makes
concurrent execution from multiple replicas' schedulers harmless: a
second replica's `updateMany` calls simply match zero rows for anything
a first replica already finalized in the same window. No distributed
lock was added, per the brief's explicit instruction not to build
anti-fraud/distributed-coordination infrastructure beyond what
correctness requires.

Tests added (3, attendance-finalizer.scheduler.spec.ts): calls
`finalizeDueRecords` once per run; repeated invocation is safe (delegates
to the already-idempotent finalizer, asserted across two calls with
different return values); a failure from `finalizeDueRecords` propagates
rather than being silently swallowed (so a real failure is visible in
logs/monitoring rather than disappearing).

G. SESSION LIFECYCLE HARDENING
================================================================================

Reviewed the complete lifecycle (SessionsService: `create`, `update`,
`markLive`, `markEnded`, `cancel`, staffing operations) against the
brief's checklist:

  - SCHEDULED -> LIVE -> ENDED, and SCHEDULED/LIVE -> CANCELED: unchanged

    ENDED from non-LIVE, CANCELED from ENDED/CANCELED). No frozen-enum
    "COMPLETED" state exists to add — ENDED already fills that role (see
    Assumptions, section A).
  - `entitlementPoint = MIN(scheduled start, cancellation time)` —
    unchanged from the Phase 2F correction round; still implemented
    exactly in `SessionsService.markLive`/`cancel` (see the Phase 2F
    review's own section P for the source, byte-for-byte unchanged by
    Phase 2G).
  - Entitlement creation idempotency: unchanged — `EntitlementService`'s
    upsert-based writes are untouched by this milestone.
  - Cancellation cannot destroy historical entitlement: unchanged —
    `SessionEntitlementSnapshot` rows are never deleted or overwritten by
    any code path touched in Phase 2G.
  - Replacement inheritance / repeated replacement chains: unchanged —
    `EntitlementService.inheritForReplacement` and
    `SessionsService.create`'s replacement wiring are untouched.
  - Recording publication lifecycle rule (`RecordingService.publish`
    requires `status === ENDED`, and the schema's own `sessionId @unique`
    on SessionRecording prevents a second publish): unchanged, already
    correct.
  - Attendance processing cannot mutate CANCELED sessions — THIS WAS THE
    ONE GENUINE GAP, now closed: `LiveAttendanceIntervalService.ingest`
    and `WatchedIntervalService.ingest` both now reject (409
    ConflictException) any ingestion attempt against a session whose
    `status === CANCELED`, before any interval row is written or any
    qualification is attempted. A CANCELED session produces no
    AttendanceRecord rows in the first place (frozen design section F),
    so this closes the one path by which a late-arriving interval could
    otherwise still write raw LiveAttendanceInterval/WatchedInterval
    evidence rows against a session the domain considers to have no
    attendance at all.

No new workflow complexity was introduced — both new guards are a single
status check each, matching the existing style of every other lifecycle
guard in this codebase.

I. RATE LIMITING
================================================================================

Mechanism: `@nestjs/throttler` (v6.5.0), the conventional NestJS-native
rate-limiting library. `ThrottlerModule.forRoot([{ name: 'default', ttl:
60_000, limit: 100 }])` registers a generous global default (100
requests/minute per client) applied via a global `APP_GUARD`
(`ThrottlerGuard`) in `app.module.ts` — every route not otherwise
annotated gets this baseline. `AuthController.login` carries its own
stricter override, `@Throttle({ default: { limit: 5, ttl: 60_000 } })` —
5 attempts per minute per client, specifically because credential-
guessing is the one endpoint worth a materially tighter limit than
everything else.

Correct throttled response: Nest's `ThrottlerGuard` returns HTTP 429 (Too
Many Requests) automatically when a client exceeds its limit — verified
directly by the new integration test hitting `/auth/login` 6 times.

No enumeration introduced: the throttled (429) response carries no
`accessToken` and is identical in shape regardless of which email was
submitted or whether that account exists — verified by a test that
throttles using a different, nonexistent email on every attempt and still
gets 429 on the 6th, proving the counter tracks the client (IP), not the
submitted account.

Deployment behind Railway/proxy: `main.ts`'s `app.set('trust proxy', 1)`
(added this milestone) is what makes per-client counting correct once
deployed behind Railway's reverse proxy — without it, every request would
appear to originate from the proxy's own address and the limiter would
throttle all callers as a single client.

Tests (3, `auth-rate-limit.http.spec.ts`, using a real `ThrottlerGuard`
and the real `@Throttle` decorator, not a stand-in): normal login within
the limit succeeds; the 6th attempt in a minute is throttled with 429 and
carries no credential-shaped body; throttling is client-scoped, not
account-scoped (proven with varying nonexistent emails).

  block previously surfaced the underlying driver error's own `.message`
  directly in the HTTP response — a realistic Postgres connection
  failure can embed a hostname, username, or connection-string fragment
  in that message, which a public readiness endpoint must never return.
  It now does two separate things: it logs the real error server-side via
  Nest's own `Logger.error` (so operators retain full diagnostic detail
  in the platform's log stream), and it returns a fixed, non-sensitive
  string — `"Database unavailable"` (the `GENERIC_DATABASE_ERROR`
  constant) — as the HTTP-visible `error` field, regardless of what the
  underlying driver actually said. Neither endpoint's body includes
  `DATABASE_URL`, `JWT_SECRET`, a hostname, a username, a password, a
  connection-string fragment, raw driver/Prisma error text, or a stack
  trace. Both endpoints remain excluded from the global `api/v1` prefix
  (`app.setGlobalPrefix('api/v1', { exclude: ['health', 'health/ready'] })`)
  so a deployment platform's health-check configuration never needs to
  know about API versioning.

`health.service.spec.ts` (5 tests, +1 from the pre-correction 4,
previously untested before Phase 2G): liveness succeeds without touching
the database; readiness succeeds when the ping succeeds; readiness
reports `degraded` (and `isServable` returns `false`) when the ping
fails, with an assertion that the service never calls
`configService.getOrThrow('DATABASE_URL')` or `'JWT_SECRET')` while
building that report; `isServable`'s exhaustive-switch behavior across
all three `HealthStatus` values; and — new, Correction 2 — a test that
throws an error containing an obvious fake secret/connection string
(`postgresql://tubi_admin:sup3r-s3cr3t-p4ssw0rd@prod-db.internal:5432/tubi`)
and asserts, via `JSON.stringify(report)`, that neither the full string
nor any of its individual sensitive fragments (password, username,
hostname) appears anywhere in the serialized response, and that the
response's `error` field is exactly `"Database unavailable"`.

================================================================================

1. Rate limiting uses `@nestjs/throttler`'s default in-memory store. This
   is correct for a single Railway instance; if the service is later
   scaled to multiple replicas, each replica counts independently, so the
   effective global rate limit scales up with replica count rather than
   staying fixed at 5/minute. Closing this fully would need a shared
   store (e.g. Redis-backed throttler storage) — explicitly out of scope
   per the brief ("do not build a distributed anti-fraud platform").

2. [RESOLVED — external review Correction 2] `HealthService.probeDatabase`
   previously passed the underlying Postgres driver's own `.message`
   through to the HTTP readiness response unmodified — a realistic
   failure mode that could expose a hostname, username, or
   connection-string fragment publicly. It now logs the real error
   server-side (`Logger.error`) and returns a fixed, non-sensitive string
   (`"Database unavailable"`) to the HTTP caller in every failure case,
   with a test (`health.service.spec.ts`) proving a thrown error
   containing an obvious fake secret/connection string cannot appear
   anywhere in the serialized response. No remaining limitation here.

3. LIVE ingestion remains ADMIN-only (Phase 2F limitation, unchanged;
   the future Zoom adapter is out of scope for both 2F and 2G).

4. No pagination on list endpoints (unchanged from Phase 2F; not named in
   the Phase 2G brief).

5. The `apps/web` foundation added this milestone
   (`NEXT_PUBLIC_API_URL`/`API_BASE_URL`) is intentionally inert — no
   fetch call, API client, or route references it yet. This is by design
   (section 12 of the brief: "do NOT build the full frontend in this
   phase"), not an oversight; the next milestone is expected to consume
   it directly.

6. No production deployment exists (section T) — this is not a code
   limitation but the expected, reported outcome of this environment
   having no Railway access.

7. Malformed-identifier handling for URL path parameters is enforced
   uniformly by `ParseUUIDPipe` at the framework level across every
   controller; this was verified by direct inspection (a repository-wide
   grep confirming every `:id`-shaped route parameter across every
   controller uses it) rather than by one dedicated unit test per
   endpoint, since the guarantee is structural (the pipe itself is
   NestJS's own, already extensively tested code) rather than
   business-logic that could regress silently per-endpoint.

import { Prisma } from '../generated/prisma/client.js';
import { PrismaService } from '../prisma/prisma.service.js';

export async function withAdvisoryLock<T>(
  prisma: PrismaService,
  lockKey: string,
  fn: (tx: Prisma.TransactionClient) => Promise<T>,
): Promise<T> {
  return prisma.$transaction(async (tx) => {
    await tx.$queryRaw`SELECT pg_advisory_xact_lock(hashtext(${lockKey})::bigint)`;
    return fn(tx);
  });
}

import 'reflect-metadata';

import { Logger, ValidationPipe } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import { NestFactory } from '@nestjs/core';
import type { NestExpressApplication } from '@nestjs/platform-express';
import helmet from 'helmet';

import { AppModule } from './app.module.js';

async function bootstrap(): Promise<void> {
  const app = await NestFactory.create<NestExpressApplication>(AppModule, { bufferLogs: true });
  const config = app.get(ConfigService);
  const logger = new Logger('Bootstrap');

  app.set('trust proxy', 1);

  app.use(helmet());

  app.enableCors({
    origin: config.getOrThrow<string[]>('corsOrigins'),
    credentials: true,
  });

  app.setGlobalPrefix('api/v1', { exclude: ['health', 'health/ready'] });

  app.useGlobalPipes(
    new ValidationPipe({
      whitelist: true,
      forbidNonWhitelisted: true,
      transform: true,
    }),
  );

  app.enableShutdownHooks();

  const port = config.getOrThrow<number>('PORT');
  await app.listen(port, '0.0.0.0');

  logger.log(`API listening on http://0.0.0.0:${port}`);
}

const GENERIC_DATABASE_ERROR = 'Database unavailable';

@Injectable()
export class HealthService {
  private readonly logger = new Logger(HealthService.name);

  // ... constructor unchanged ...

  async getReadiness(): Promise<HealthReport> {
    const database = await this.probeDatabase();
    const status: HealthStatus = database.status === 'ok' ? 'ok' : 'degraded';
    return this.buildReport(status, [database]);
  }

  private async probeDatabase(): Promise<DependencyHealth> {
    const startedAt = performance.now();
    try {
      await this.prisma.ping();
      return {
        name: 'postgresql',
        status: 'ok',
        latencyMs: Math.round(performance.now() - startedAt),
      };
    } catch (error) {
      // The underlying pg/Prisma driver's error message can embed
      // hostnames, usernames, or connection-string fragments — a public
      // readiness endpoint must never return that. The real error is
      // logged server-side (operators can read it there); the HTTP
      // response gets only the fixed, non-sensitive
      // GENERIC_DATABASE_ERROR string, regardless of what the driver
      // actually said.
      this.logger.error(
        `Database readiness probe failed: ${error instanceof Error ? error.message : String(error)}`,
      );

      return {
        name: 'postgresql',
        status: 'down',
        latencyMs: Math.round(performance.now() - startedAt),
        error: GENERIC_DATABASE_ERROR,
      };
    }
  }
