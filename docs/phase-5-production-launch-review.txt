     Frontend: `/admin/offerings` page (create form + course checklist +
     existing-offerings list).

  2. Notification operations (ADMIN visibility + narrowly-scoped retry).
       - `GET /admin/notifications?status=` — lists outbox items (PENDING /
         SENDING / SENT / FAILED), most recent 200, joined with recipient
         email/name, including attempts and last error.
       - `POST /admin/notifications/:id/retry` — resets ONE FAILED item back
         to PENDING, clearing the existing claim-token/claimedAt fencing
         columns and the attempt counter, so the existing fenced dispatch
         scheduler can safely reclaim it. Rejects (409) anything not
         currently FAILED, including a race where another actor changed its
         state between the read and the write (compound conditional
         `updateMany` with a re-check, not a blind write).
     Frontend: `/admin/notifications` page (status filter + retry button on
     FAILED rows only).

  3. Launch operations dashboard.
       - `GET /admin/operations` — a single compact report: database
         reachability, Zoom/Paystack/SMTP "configured" booleans (never a
         credential value), count of sessions stuck in FAILED meeting
         provisioning, count of permanently-FAILED notifications, count of
         PENDING payments, count of upcoming SCHEDULED sessions.
     Frontend: `/admin/operations` page.

  4. ADMIN school-setup audit (no new code required).
     Confirmed GradeLevel, AcademicTerm, Subject, Course, Teacher, and
     Session already have full create/read/update(/delete where applicable)
     ADMIN API + frontend paths from Phases 2D/2E/3/4 — no direct database
     access is required to run the school. Offering was the only genuine
     gap, now closed (item 1 above).

  5. Production-verification pass (read-only; no code changes) — see
     sections E, F, G, H.

  6. Codex correction pass (four findings from the first-review inspection
     of items 1–3 above, all now fixed and covered by new automated tests):
       a. Operations database-down handling. `OperationsService.getReport()`
          now probes the database FIRST; if it is down, all four operational
          counts are returned as `null` ("unavailable") WITHOUT ever issuing
          the count queries, rather than either attempting them against an
          unreachable database or silently reporting a misleading `0`. The
          `/admin/operations` page renders a `null` count as "Unavailable".
          See sections Q, S, Z.
       b. Offering course concurrency. `addCourse`/`removeCourse` still keep
          their fast-path `findUnique` pre-check, but now also catch the
          Prisma constraint error a genuine race can produce past that
          check: a concurrent duplicate `create` raises `P2002`, caught and
          turned into the same 409 `ConflictException` a sequential
          duplicate gets; a concurrent/already-absent `delete` raises
          `P2025`, caught and turned into the same 404 `NotFoundException`
          a sequential double-removal gets. Any other error still
          propagates unchanged. See sections B, Z, AC.
       c. Notification response minimization. `NotificationsService.listAll`
          and `retryFailed` now both select/project an explicit minimized
          shape (id, type, recipientUserId, status, attempts, createdAt,
          sentAt, lastError, recipient) — `claimToken`, `claimedAt` (internal
          dispatcher-fencing state), and `payload` are never selected from
          the database and never reach the controller or the browser. See
          section Q.
       d. Offering-name whitespace validation. Both `CreateOfferingDto` and
          `UpdateOfferingDto` now `@Transform` the `name` field (trim) before
          `@MinLength(1)` validates it, so a whitespace-only value (e.g.
          three spaces) collapses to an empty string and is rejected with a
          400, rather than being accepted as a "real" Offering name. A name
          with incidental leading/trailing whitespace is silently trimmed
          rather than rejected. See section AC.

--- apps/api/src/notifications/notifications.service.ts (retryFailed, and
    the minimized shape/projection it and listAll now share — Codex
    finding 3, corrected this pass) --------------------------------------
  export interface NotificationOutboxItemWithRecipient {
    id: string;
    type: string;
    recipientUserId: string;
    status: NotificationStatus;
    attempts: number;
    createdAt: Date;
    sentAt: Date | null;
    lastError: string | null;
    recipient: { id: string; email: string; fullName: string } | null;
  }
  // NOTE: no `claimToken`, `claimedAt`, or `payload` field exists on this
  // interface at all — not merely unpopulated. The dispatcher-fencing
  // columns and the raw notification payload never leave the database
  // layer for this ADMIN-facing shape.

  async retryFailed(id: string): Promise<NotificationOutboxItemWithRecipient> {
    const item = await this.prisma.notificationOutboxItem.findUnique({ where: { id } });
    if (!item) {
      throw new NotFoundException(`Notification ${id} not found`);
    }
    if (item.status !== NotificationStatus.FAILED) {
      throw new ConflictException(
        `Notification ${id} is ${item.status}, not FAILED — only permanently-failed notifications can be retried`,
      );
    }

    const { count } = await this.prisma.notificationOutboxItem.updateMany({
      where: { id, status: NotificationStatus.FAILED },
      data: {
        status: NotificationStatus.PENDING,
        claimToken: null,
        claimedAt: null,
        attempts: 0,
        lastError: null,
      },
    });
    if (count === 0) {
      throw new ConflictException(
        `Notification ${id} is no longer FAILED — it may already be retrying`,
      );
    }

    const [refreshed] = await this.listAllByIds([id]);
    if (!refreshed) {
      throw new NotFoundException(`Notification ${id} not found after retry`);
    }
    return refreshed;
  }

  private async listAllByIds(ids: string[]): Promise<NotificationOutboxItemWithRecipient[]> {
    const items = await this.prisma.notificationOutboxItem.findMany({
      where: { id: { in: ids } },
      select: {
        id: true, type: true, recipientUserId: true, status: true,
        attempts: true, createdAt: true, sentAt: true, lastError: true,
        // claimToken, claimedAt, payload deliberately NOT selected.
      },
    });
    /* ...joins recipient identity, same as listAll (see section Q)... */
  }

clause rather than trusting the earlier `findUnique` read — a
time-of-check/time-of-use race where the dispatcher independently claims the
item between the read and the write is caught (`count === 0`) rather than
silently overwriting an in-flight dispatch attempt. Separately (Codex
finding 3), `retryFailed`'s response now goes through the same minimized
`select` as `listAll` — the mutation endpoint returns exactly what the
listing endpoint returns, and neither ever includes the two internal
fencing columns this method itself just wrote to.

--- apps/api/src/offerings/offerings.service.ts (addCourse/removeCourse —
    Prisma constraint-race handling, Codex finding 2, corrected this pass) --
  async addCourse(id: string, dto: AddOfferingCourseDto): Promise<OfferingWithCourses> {
    await this.findOne(id);
    await this.assertCoursesExist([dto.courseId]);

    const existing = await this.prisma.offeringCourse.findUnique({
      where: { offeringId_courseId: { offeringId: id, courseId: dto.courseId } },
    });
    if (existing) {
      throw new ConflictException(`Course ${dto.courseId} is already part of offering ${id}`);
    }

    try {
      await this.prisma.offeringCourse.create({ data: { offeringId: id, courseId: dto.courseId } });
    } catch (error) {
      if (error instanceof Prisma.PrismaClientKnownRequestError && error.code === 'P2002') {
        throw new ConflictException(`Course ${dto.courseId} is already part of offering ${id}`);
      }
      throw error;
    }
    return this.findOneWithCourses(id);
  }

  async removeCourse(id: string, courseId: string): Promise<OfferingWithCourses> {
    await this.findOne(id);
    const existing = await this.prisma.offeringCourse.findUnique({
      where: { offeringId_courseId: { offeringId: id, courseId } },
    });
    if (!existing) {
      throw new NotFoundException(`Course ${courseId} is not part of offering ${id}`);
    }

    try {
      await this.prisma.offeringCourse.delete({
        where: { offeringId_courseId: { offeringId: id, courseId } },
      });
    } catch (error) {
      if (error instanceof Prisma.PrismaClientKnownRequestError && error.code === 'P2025') {
        throw new NotFoundException(`Course ${courseId} is not part of offering ${id}`);
      }
      throw error;
    }
    return this.findOneWithCourses(id);
  }
------------------------------------------------------------------------------
Why this matters: the `findUnique` pre-check remains a fast path for the
uncontended case, but is explicitly NOT the correctness guarantee — two
simultaneous requests can both pass it. The composite unique constraint on
`(offeringId, courseId)` is what Postgres actually enforces; the `catch`
turns the resulting `P2002` (duplicate attach) or `P2025` (already-removed
detach) into the same 409/404 a sequential duplicate/double-removal would
get, rather than letting a raw database constraint violation escape as an
unhandled 500. Any other error is re-thrown unchanged — this is a narrow
catch on a specific Prisma error code, not a generic error swallower.

Why this matters: `@Transform` runs before `@MinLength` in the global
`ValidationPipe`'s `transform: true` pipeline (apps/api/src/main.ts), so a
