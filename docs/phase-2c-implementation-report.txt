CORRECTION PASS SUMMARY (applied after the first external review)
================================================================================

FOUNDER RULING — account provisioning (now FROZEN):
  Public self-registration may create LEARNER accounts only. TEACHER and
  ADMIN accounts must NOT be publicly self-registerable; they will be
  provisioned later through controlled, non-public administrative
  workflows. The existing implementation (hardcoding public registration to
  RoleName.LEARNER) already satisfied this and required no code change —
  it is now approved and frozen rather than an open assumption (see the
  superseded item in section I).

REQUIRED HARDENING 1 — Explicit JWT algorithm (implemented):
  JWT signing and verification are now both pinned to HS256 via a single
  shared constant (JWT_ALGORITHM in jwt.constants.ts), rather than relying
  on library defaults. A token signed with any other algorithm is rejected
  even if it carries the correct secret. New tests prove both directions
  (section E).

REQUIRED HARDENING 2 — Email canonicalization (implemented):
  AuthService now normalizes every email (trim + lowercase) via a single
  `normalizeEmail()` function, applied identically before every lookup and
  before every write, in both `register` and `login`. New tests prove
  case/whitespace variations resolve to the same account. No change was
  made to the frozen Prisma domain schema — normalization happens entirely
  in the service layer, before the value ever reaches Prisma.

REQUIRED HARDENING 3 — Duplicate registration race (implemented):
  The friendly pre-check (`findUnique` before `create`) is retained, but
  `register` now also wraps `prisma.user.create` in a try/catch that
  detects a Prisma unique-constraint violation (error code P2002) and
  translates it into the same `ConflictException` (409) the pre-check
  would have produced. Any other database error is re-thrown unchanged —
  it is not swallowed or reinterpreted as a duplicate. New tests cover both
  the race itself and the passthrough of unrelated errors.

NON-BLOCKING / DEFERRED, unchanged by this pass, per explicit instruction:
  - bcryptjs at cost factor 12 was kept as-is.
  - Rate limiting / brute-force protection remains an open item, required
    before public production exposure, not blocking this freeze.
  - The Turbo `spawn UNKNOWN` issue remains outside Phase 2C's scope.

B. AUTHENTICATION ARCHITECTURE IMPLEMENTED
================================================================================

Module structure (apps/api/src/auth/):
  auth.module.ts              Wires PassportModule + JwtModule (async,
                               secret/expiry/algorithm from ConfigService)
                               around the controller/service/strategy.
  auth.controller.ts           HTTP surface: register, login, me.
  auth.service.ts               All business logic: registration, credential
                               verification, token issuance, current-user
                               lookup, email canonicalization, duplicate-
                               race handling. Owns the one function
                               permitted to read `passwordHash` off a row
                               (`sanitizeUser`).
  jwt.constants.ts              Single source of truth for the pinned JWT
                               algorithm (HS256), imported by both the
                               signing module config and the verification
                               strategy. [added in correction pass]
  strategies/jwt.strategy.ts    Passport "jwt" strategy: verifies the bearer
                               token's signature, expiry, AND algorithm
                               (allow-list), then re-fetches the user from
                               the database on every request.
  guards/jwt-auth.guard.ts      Thin `AuthGuard('jwt')` wrapper — require a
                               valid bearer token.
  guards/roles.guard.ts         Reads `@Roles(...)` metadata and checks
                               `request.user.role` against it.
  decorators/roles.decorator.ts        `@Roles('ADMIN', ...)` — declares
                               required roles via Nest metadata.
  decorators/current-user.decorator.ts `@CurrentUser()` — pulls the
                               authenticated user off the request.
  dto/register.dto.ts, dto/login.dto.ts  class-validator input contracts.
  types.ts                      JwtPayload / AuthenticatedUser /
                               SanitizedUser — the only shapes that flow
                               between layers.

Registration flow (updated by the correction pass):
  1. AuthController.register receives a validated RegisterDto (email,
     password, fullName — no role field exists on the DTO at all).
  2. AuthService.register normalizes the email (trim + lowercase) via
     `normalizeEmail()`.
  3. It checks for an existing user by the normalized email and throws
     ConflictException (409) if found — this is the friendly pre-check,
     not the sole protection (see step 5).
  4. The password is hashed with bcryptjs at cost factor 12.
  5. A User row is created with `role: RoleName.LEARNER` — hardcoded, never
     read from the request — inside a try/catch. If Prisma reports a
     unique-constraint violation (code P2002) on the insert itself (i.e.
     the pre-check's race window was lost to a concurrent request), the
     same ConflictException(409) is thrown. Any other error from `create`
     is re-thrown unchanged, never masked as a duplicate.
  6. The created row is passed through `sanitizeUser` (strips passwordHash)
     before returning.
  FOUNDER RULING: registration is LEARNER-only, and this is now frozen —
  see the Correction Pass Summary above. This is no longer an open
  assumption.

Login flow (updated by the correction pass):
  1. AuthController.login receives a validated LoginDto.
  2. AuthService.login normalizes the submitted email the same way
     registration does, then looks the user up by that normalized email.
  3. If no user exists, or the user is `isActive: false`, the same
     UnauthorizedException("Invalid email or password") is thrown as for a
     wrong password — see section D.
  4. Otherwise the submitted password is compared against the stored bcrypt
     hash with `bcrypt.compare`. A mismatch throws the same 401 with the
     same message.
  5. On success, a JWT is signed (HS256, pinned) with `{ sub, email, role }`
     and returned alongside the sanitized user.

JWT issuance and validation (algorithm pinning added by the correction pass):
  - Issuance: `JwtModule.registerAsync` configures `@nestjs/jwt`'s
    `JwtService` with `secret`, `signOptions.algorithm: JWT_ALGORITHM`
    (HS256), and `signOptions.expiresIn` sourced from `ConfigService`.
    `AuthService` calls `jwtService.signAsync(payload)`, inheriting these
    module defaults.
  - Validation: `JwtStrategy` (passport-jwt `Strategy`) is now constructed
    with `algorithms: [JWT_ALGORITHM]` in addition to the secret and
    `ignoreExpiration: false`. It extracts the bearer token, verifies its
    signature, expiry, AND algorithm using the same `JWT_SECRET`/
    `JWT_ALGORITHM`, and on success invokes `validate(payload)`, which
    re-fetches the user from PostgreSQL by `payload.sub` and re-checks
    `isActive`. Only a minimal `AuthenticatedUser` (no passwordHash) is
    attached to `request.user`. A token signed with any algorithm other
    than HS256 — even carrying the correct secret — is rejected at
    verification before `validate()` is ever invoked.

/auth/me flow: unchanged by the correction pass. Guarded by `JwtAuthGuard`.
  On success, `@CurrentUser()` supplies the already-verified
  `AuthenticatedUser.id` to `AuthService.findSanitizedById`, which
  re-reads the user and returns the sanitized shape.

Password hashing approach: bcryptjs (pure-JavaScript bcrypt
implementation), cost factor 12, applied in AuthService.register only.
Unchanged by the correction pass, per explicit instruction (non-blocking/
deferred).

Authentication guard: `JwtAuthGuard` (`@nestjs/passport`'s
`AuthGuard('jwt')`). Applied per-route via `@UseGuards(JwtAuthGuard)`
(currently on `GET /auth/me` only).

Role guard/decorator: `RolesGuard` + `@Roles(...)`. Unchanged by the
correction pass. Not yet applied to any route (no role-restricted endpoint
exists yet to protect) — implemented and unit-tested as reusable
infrastructure.

Inactive users: unchanged by the correction pass. Enforced in three
independent places — AuthService.login, JwtStrategy.validate, and
AuthService.findSanitizedById — all with the same outward rejection
behavior.

C. ENDPOINTS IMPLEMENTED
================================================================================

Unchanged by the correction pass except where noted (email is now
canonicalized server-side before lookup/storage; this is transparent to the
request/response contract below — a client may still submit any casing/
whitespace and will get the same outcome as if it had submitted the
canonical form).

1) POST /auth/register
   Authentication required: No (public).
   Authorization required: None.
   Request body (application/json):
     { "email": string, "password": string (8-72 chars), "fullName": string (1-200 chars) }
   Success response: 201 Created
     { "id", "email", "fullName", "role": "LEARNER", "isActive", "createdAt", "updatedAt" }
     (never includes passwordHash; "email" reflects the normalized,
     trimmed+lowercased value, not necessarily byte-identical to what the
     client submitted)
   Error responses:
     400 Bad Request  — DTO validation failure (missing/invalid field, or an
                        unrecognised field, since the global ValidationPipe
                        uses whitelist + forbidNonWhitelisted; this is what
                        stops a client-supplied "role" field from doing
                        anything other than being rejected outright before
                        it ever reaches the service).
     409 Conflict      — email already registered, whether detected by the
                        pre-check or by a database unique-constraint
                        violation surfaced during a concurrent-registration
                        race (both now produce the identical response —
                        see Hardening 3).

2) POST /auth/login
   Authentication required: No (public).
   Authorization required: None.
   Request body: { "email": string, "password": string }
   Success response: 200 OK
     { "accessToken": string, "user": { ...sanitized user, no passwordHash } }
   Error responses:
     400 Bad Request     — DTO validation failure.
     401 Unauthorized     — unknown email (post-normalization), wrong
                            password, or inactive account — always the
                            identical message "Invalid email or password"
                            (see section D).

3) GET /auth/me
   Authentication required: Yes — `Authorization: Bearer <accessToken>`.
   Authorization required: None beyond being authenticated (any role).
   Request body: none.
   Success response: 200 OK
     { "id", "email", "fullName", "role", "isActive", "createdAt", "updatedAt" }
     (never includes passwordHash)
   Error responses:
     401 Unauthorized — no token, malformed token, expired token, invalid
                        signature, a token signed with an algorithm other
                        than the pinned HS256 (new in this pass), or the
                        token's subject no longer resolves to an active
                        user.

D. SECURITY CONTROLS IMPLEMENTED
================================================================================

Password hashing algorithm/library: bcryptjs (pure-JS bcrypt), salt rounds =
12. Unchanged by the correction pass (explicitly non-blocking/deferred).

JWT algorithm/configuration: HS256, now EXPLICITLY PINNED on both sides via
a single shared constant (`JWT_ALGORITHM` in jwt.constants.ts) — no longer
relying on library defaults. `AuthModule`'s `JwtModule.registerAsync` sets
`signOptions.algorithm: JWT_ALGORITHM`; `JwtStrategy` sets
`algorithms: [JWT_ALGORITHM]`. A token signed with any other algorithm,
including one an attacker crafts while knowing the correct secret, is
rejected at verification. Proven by new tests (section E).

JWT expiry: `JWT_EXPIRES_IN`, environment-configurable, default `"1d"`.
Unchanged by the correction pass.

Secret handling: unchanged by the correction pass — `JWT_SECRET` read only
from `process.env` via `ConfigService`, validated at startup (min 32
chars), never logged, `.env` git-ignored and uncommitted.

Startup environment validation: unchanged — `JWT_SECRET`/`JWT_EXPIRES_IN`
are part of `environmentSchema`, gating Nest's boot.

passwordHash serialization protection: unchanged — enforced structurally
via `sanitizeUser`, verified by tests at both unit and full-HTTP-response
level.

Duplicate-email handling — UPDATED by Hardening 3: the pre-check
(`findUnique` before `create`) is retained as a fast, friendly path, but is
no longer the sole protection. `prisma.user.create` is wrapped in a
try/catch; a Prisma `PrismaClientKnownRequestError` with code `P2002`
(unique-constraint violation) is caught and translated into the identical
`ConflictException('An account with this email already exists')` the
pre-check produces. This closes the TOCTOU race where two concurrent
registration requests both pass the pre-check before either has written —
previously this would have surfaced as an unhandled Prisma error (a 500
with implementation details potentially leaking); now both concurrent
callers see the same clean 409. Any other error from `create` is
re-thrown as-is (verified by a dedicated test — see section E) so this
change cannot accidentally mask a genuine database failure as "duplicate
email".

Invalid-credential handling: unchanged — a non-existent email (post-
normalization), a wrong password, and an inactive account's correct
password all throw the identical `UnauthorizedException('Invalid email or
password')`.

Inactive-user handling: unchanged — see section B.

Public registration restrictions — NOW FOUNDER-APPROVED AND FROZEN:
`RegisterDto` has no `role` field at all; `AuthService.register` hardcodes
`role: RoleName.LEARNER` with no conditional path. The founder ruling in
this correction pass makes this the confirmed, frozen behavior rather than
an implementation assumption pending review (see section I — the prior
open item is now closed).

ADMIN creation protection: unchanged — no code path, public or otherwise,
in this milestone can create a `RoleName.ADMIN` user.

Role-based authorization behavior: unchanged — see section B/E.

Email canonicalization — NEW, Hardening 2: `normalizeEmail(email)` (trim +
lowercase) is applied by `AuthService` before every database lookup and
every write, identically in `register` and `login`. This guarantees
"Learner@Example.com", " learner@example.com ", and "learner@example.com"
all resolve to exactly one account regardless of which endpoint or which
casing/whitespace variant is used first. This was implemented entirely in
the service layer — no change was made to the frozen Prisma schema
(`User.email` remains a plain unique `String` column; normalization happens
before the value ever reaches Prisma, so the column continues to store
whatever canonical form the service decides, with no schema-level
case-insensitive-collation requirement introduced).

export const JWT_ALGORITHM = 'HS256';

import { Injectable, UnauthorizedException } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import { PassportStrategy } from '@nestjs/passport';
import { ExtractJwt, Strategy } from 'passport-jwt';

import { PrismaService } from '../../prisma/prisma.service.js';
import { JWT_ALGORITHM } from '../jwt.constants.js';
import type { AuthenticatedUser, JwtPayload } from '../types.js';

@Injectable()
export class JwtStrategy extends PassportStrategy(Strategy) {
  constructor(
    configService: ConfigService,
    private readonly prisma: PrismaService,
  ) {
    super({
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
      ignoreExpiration: false,
      secretOrKey: configService.getOrThrow<string>('JWT_SECRET'),
      // Explicit allow-list, matching AuthModule's signing algorithm. A
      // token signed with any other algorithm — including one an attacker
      // crafted to try to bypass verification — is rejected outright.
      algorithms: [JWT_ALGORITHM],
    });
  }

  /**
   * Runs on every authenticated request. Re-checking the database — rather
   * than trusting the token's claims for the whole of its lifetime — is what
   * lets a deactivated account lose access immediately instead of waiting
   * for its token to expire.
   */
  async validate(payload: JwtPayload): Promise<AuthenticatedUser> {
    const user = await this.prisma.user.findUnique({ where: { id: payload.sub } });

    if (!user || !user.isActive) {
      // Same message whether the account was deleted, deactivated, or never
      // existed — an authenticated caller learns nothing more specific.
      throw new UnauthorizedException('Invalid or expired session');
    }

    return {
      id: user.id,
      email: user.email,
      fullName: user.fullName,
      role: user.role,
      isActive: user.isActive,
    };
  }
}

import { ConflictException, Injectable, UnauthorizedException } from '@nestjs/common';
import { JwtService } from '@nestjs/jwt';
import * as bcrypt from 'bcryptjs';

import { PrismaService } from '../prisma/prisma.service.js';
import { Prisma, RoleName, type User } from '../generated/prisma/client.js';
import type { LoginDto } from './dto/login.dto.js';
import type { RegisterDto } from './dto/register.dto.js';
import type { JwtPayload, SanitizedUser } from './types.js';

/** Cost factor for bcrypt hashing. 12 is the current widely-recommended
 * floor for production password storage as of this writing. */
const BCRYPT_SALT_ROUNDS = 12;

/** Generic message for every credential failure. Login and inactive-account
 * rejection must be indistinguishable to the caller — telling an attacker
 * "that email exists but the password is wrong" versus "no such account"
 * hands them a free account-enumeration oracle. */
const INVALID_CREDENTIALS_MESSAGE = 'Invalid email or password';

const DUPLICATE_EMAIL_MESSAGE = 'An account with this email already exists';

/** Prisma's error code for a unique-constraint violation. */
const PRISMA_UNIQUE_CONSTRAINT_ERROR_CODE = 'P2002';

/**
 * Canonicalizes an email identifier before every lookup or write.
 *
 * Registration and login must apply the exact same rule, or
 * "Learner@Example.com " and "learner@example.com" would silently behave as
 * two different accounts depending on which endpoint happened to see which
 * casing/whitespace first.
 */
function normalizeEmail(email: string): string {
  return email.trim().toLowerCase();
}

@Injectable()
export class AuthService {
  constructor(
    private readonly prisma: PrismaService,
    private readonly jwtService: JwtService,
  ) {}

  /**
   * Public self-registration.
   *
   * Always creates a LEARNER account. There is no code path — regardless of
   * what a request body contains — through which a public caller can create
   * a TEACHER or ADMIN account. See the Phase 2C completion report for the
   * founder-review item this reflects: TEACHER/ADMIN provisioning is
   * deliberately out of scope here and belongs to a later, non-public flow.
   */
  async register(dto: RegisterDto): Promise<SanitizedUser> {
    const email = normalizeEmail(dto.email);
    const existing = await this.prisma.user.findUnique({ where: { email } });

    if (existing) {
      throw new ConflictException(DUPLICATE_EMAIL_MESSAGE);
    }

    const passwordHash = await bcrypt.hash(dto.password, BCRYPT_SALT_ROUNDS);

    let user: User;
    try {
      user = await this.prisma.user.create({
        data: {
          email,
          passwordHash,
          fullName: dto.fullName,
          role: RoleName.LEARNER,
        },
      });
    } catch (error) {
      // The findUnique check above narrows the window but does not close
      // it — two requests can both pass it before either writes. Prisma's
      // own unique-constraint violation is the authoritative guard; a
      // caller must see the same 409 either way, never a raw database
      // error.
      if (isUniqueConstraintViolation(error)) {
        throw new ConflictException(DUPLICATE_EMAIL_MESSAGE);
      }
      throw error;
    }

    return sanitizeUser(user);
  }

  async login(dto: LoginDto): Promise<{ accessToken: string; user: SanitizedUser }> {
    const email = normalizeEmail(dto.email);
    const user = await this.prisma.user.findUnique({ where: { email } });

    // Reject a non-existent account and an inactive one with the same
    // outcome and the same message — see INVALID_CREDENTIALS_MESSAGE.
    if (!user || !user.isActive) {
      throw new UnauthorizedException(INVALID_CREDENTIALS_MESSAGE);
    }

    const passwordMatches = await bcrypt.compare(dto.password, user.passwordHash);

    if (!passwordMatches) {
      throw new UnauthorizedException(INVALID_CREDENTIALS_MESSAGE);
    }

    const payload: JwtPayload = { sub: user.id, email: user.email, role: user.role };
    const accessToken = await this.jwtService.signAsync(payload);

    return { accessToken, user: sanitizeUser(user) };
  }

  async findSanitizedById(userId: string): Promise<SanitizedUser> {
    const user = await this.prisma.user.findUnique({ where: { id: userId } });

    if (!user || !user.isActive) {
      throw new UnauthorizedException('Invalid or expired session');
    }

    return sanitizeUser(user);
  }
}

/** True for a Prisma unique-constraint violation (e.g. two concurrent
 * registrations racing on the same email) — the case `register` must fold
 * into the same 409 Conflict a pre-check would have produced. */
function isUniqueConstraintViolation(error: unknown): boolean {
  return (
    error instanceof Prisma.PrismaClientKnownRequestError &&
    error.code === PRISMA_UNIQUE_CONSTRAINT_ERROR_CODE
  );
}

/** The only function in this module allowed to read `passwordHash` off a
 * `User` row — every value that leaves the service goes through this. */
function sanitizeUser(user: User): SanitizedUser {
  return {
    id: user.id,
    email: user.email,
    fullName: user.fullName,
    role: user.role,
    isActive: user.isActive,
    createdAt: user.createdAt,
    updatedAt: user.updatedAt,
  };
}

      fullName: 'Learner Three',
    });

    const response = await request(server())
      .post('/auth/login')
      .send({ email: 'learner3@example.com', password: 'wrong-password' });

    expect(response.status).toBe(401);
  });

  it('rejects login for a deactivated account', async () => {
    const passwordHash = await bcrypt.hash('correct-horse-battery-staple', 4);
    const inactive = buildUser({ email: 'inactive@example.com', passwordHash, isActive: false });
    users.set(inactive.id, inactive);

    const response = await request(server())
      .post('/auth/login')
      .send({ email: 'inactive@example.com', password: 'correct-horse-battery-staple' });

    expect(response.status).toBe(401);
  });

  it('returns the current user for a valid bearer token, without passwordHash', async () => {
    await request(server()).post('/auth/register').send({
      email: 'me@example.com',
      password: 'correct-horse-battery-staple',
      fullName: 'Me User',
    });
    const login = await request(server())
      .post('/auth/login')
      .send({ email: 'me@example.com', password: 'correct-horse-battery-staple' });

    const response = await request(server())
      .get('/auth/me')
      .set('Authorization', `Bearer ${bodyOf(login).accessToken}`);

    expect(response.status).toBe(200);
    expect(bodyOf(response).email).toBe('me@example.com');
    expect(response.body).not.toHaveProperty('passwordHash');

    const response = await request(server()).get('/auth/me');

    expect(response.status).toBe(401);

    expect(response.status).toBe(401);

  it('rejects a token signed with a different algorithm, even with the correct secret', async () => {
    await request(server()).post('/auth/register').send({
      email: 'wrongalg@example.com',
      password: 'correct-horse-battery-staple',
      fullName: 'Wrong Alg',
    });

    // Same JwtService instance the app uses, but explicitly signed with a
    // different algorithm than JwtStrategy's pinned allow-list (HS256).
    // If verification only checked the secret, this token would pass; the
    // algorithm allow-list is what must reject it.
    const jwtService = new JwtService({ secret: TEST_JWT_SECRET });
    const foreignAlgorithmToken = await jwtService.signAsync(
      { sub: 'does-not-matter', email: 'wrongalg@example.com', role: RoleName.LEARNER },
      { algorithm: 'HS384' },
    );

    const response = await request(server())
      .get('/auth/me')
      .set('Authorization', `Bearer ${foreignAlgorithmToken}`);

    expect(response.status).toBe(401);
  });
