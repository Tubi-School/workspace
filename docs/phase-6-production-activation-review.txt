0. SURGICAL HOTFIX — PRODUCTION BOOTSTRAP FAILURE (void-deserialization)
================================================================================

The operator's first real production bootstrap attempt failed before
creating any ADMIN row, with:

    Invalid `prisma.$queryRaw()` invocation
    Raw query failed:
    Failed to deserialize column of type 'void'

Exact root cause: `acquireBootstrapAdminLock` (the function taking the
transaction-scoped advisory lock — see section 1/8) used
`tx.$queryRaw`SELECT pg_advisory_xact_lock(...)`;`. `pg_advisory_xact_lock`
returns PostgreSQL's `void` type. `$queryRaw` always attempts to
deserialize every returned column into a typed JS value; `void` has no
such mapping, so the call fails on every invocation — reproduced against a
real PostgreSQL database (this session's own Neon development instance,
not production) with the identical error text quoted above, confirming
this is a deterministic client-side deserialization defect, not a
transient or environment-specific failure.

Fix applied (smallest correct form, no architecture change): replaced
`tx.$queryRaw` with `tx.$executeRaw` for this one statement. `$executeRaw`
executes the identical SQL and reports only the affected-row count; it
never attempts to deserialize a result column, so the `void` return value
is simply never inspected. PostgreSQL performs the exact same lock
acquisition either way — this is purely a difference in how the Node
driver reads back an (irrelevant) result, not a difference in server-side
behavior. Re-verified by running the fixed function against the same real
database: the lock now acquires successfully with no error.

The lock acquisition was extracted into its own exported function,
`acquireBootstrapAdminLock(tx)`, called as the first statement inside the
`$transaction` callback in `main()` — unchanged position, unchanged
transaction-scoped semantics (still released automatically on commit or
rollback), unchanged fixed lock key. This was done only so a test could
assert the exact call shape (`$executeRaw`, not `$queryRaw`) without a
real database connection — see section 9.

Control-flow confirmation that the failed attempt could not have reached
the ADMIN insert: `acquireBootstrapAdminLock(tx)` is the FIRST statement
inside the `$transaction` callback — it runs before the existing-ADMIN
`findFirst`, before the email-uniqueness `findUnique`, and before
`user.create`. Because it threw synchronously, none of those three later
statements executed at all; Prisma's interactive-transaction wrapper
caught the throw, issued a rollback, and re-threw the same error out of
`prisma.$transaction(...)` — so `const result = await prisma.$transaction(...)`
itself never returned, and the `switch (result.outcome)` block that would
call `user.create` (in the `'created'` branch) was never reached. Zero
durable writes occurred against production during the failed attempt.

This hotfix does not change: standalone-CLI-only architecture, absence of
any HTTP bootstrap endpoint, transaction-scoped (`pg_advisory_xact_lock`)
locking, concurrency-safety of first-admin creation, LEARNER-only public
registration, or the existing-ADMIN/duplicate-email safeguards. No secret
value was printed at any point during reproduction or verification — only
error message text and success/failure booleans.

The ADMIN bootstrap was NOT re-run against production from this session —
this environment still has no Railway/production database access. The fix
is implemented, typechecked, linted, built, unit-tested, and additionally
verified against a real (non-production) PostgreSQL database.

--------------------------------------------------------------------------------
EMAIL NORMALIZATION FINDING AND FIX (Codex final-review finding, HIGH)
--------------------------------------------------------------------------------

Finding: the script trimmed but did not lowercase the email. `AuthService`
normalizes every email to `trim().toLowerCase()` before every lookup or
write (both `register` and `login`). Without the same normalization here,
running this script with `--email Admin@School.Example` would create a
`User` row with that exact mixed-case email, while the normal login path
looks up `admin@school.example` — the two would never match, and the
created ADMIN account would be unable to log in at all.

Fix applied: `parseArgs` now returns `email.trim().toLowerCase()` instead
of `email.trim()` — normalization happens at the single point every
downstream use (validation, the duplicate-email lookup inside the locked
transaction, and the `user.create` call) reads from, so all three are
correctly normalized by construction rather than needing three separate
fixes. This exactly mirrors `AuthService`'s `normalizeEmail()` behavior.
See section 8 for the exact source and section 9 for the two new tests
proving `Admin@School.Example` becomes `admin@school.example`.

CONCURRENCY FINDING AND FIX (ChatGPT first-review request)
--------------------------------------------------------------------------------

Question asked: could two simultaneous bootstrap processes both observe
"no ADMIN exists" and then each create one?

Finding: YES, in the version reviewed. The original implementation ran the
existing-ADMIN check (`prisma.user.findFirst({ where: { role: 'ADMIN' } })`)
and the eventual `prisma.user.create(...)` as two independent, unserialized
round trips. Two processes started close together could both execute the
check before either had inserted anything, both see zero ADMIN rows, and
both proceed to create one (with different `--email` values, since the
`User.email` unique constraint would only stop a second process using the
SAME email, not a second ADMIN under a different email). This is a
classic time-of-check/time-of-use (TOCTOU) race. It was not previously
prevented by any schema constraint — `role` has no uniqueness constraint,
by design, since more than one ADMIN is a legitimate end state.

Fix applied (smallest possible, no schema change): the existing-ADMIN
check, the email-uniqueness check, and the insert are now performed inside
a single Prisma `$transaction`, which first takes a transaction-scoped
PostgreSQL advisory lock (`pg_advisory_xact_lock`, keyed to the fixed
string `"tubi:bootstrap-admin"`) before either read. This is the same
primitive already used elsewhere in this codebase for check-then-write
races (`apps/api/src/common/pg-advisory-lock.util.ts`, used by
`SubscriptionAccess` grant and live-attendance interval ingestion). The
lock is automatically released when the transaction commits or rolls back
— there is no manual unlock/cleanup path, and no schema change is required
(it is a Postgres session primitive, not a table).

Why this closes the race: `pg_advisory_xact_lock` blocks the *second*
concurrent transaction at the `SELECT pg_advisory_xact_lock(...)` line
until the *first* transaction commits or rolls back. The second
transaction's existing-ADMIN check therefore only ever runs after the
first transaction's outcome (whether it created an ADMIN or refused) is
already durable — it is structurally impossible for the second process to
observe "no ADMIN exists" while the first is still mid-flight toward
creating one. Password acquisition (the interactive prompt) and hashing
remain outside the transaction/lock, since they are human I/O with nothing
to do with database consistency and no reason to hold a lock open while
waiting on a person to type.

See section 8 below for the exact, current source.

--- Email normalization (Codex HIGH finding fix — matches
    AuthService.normalizeEmail() exactly: trim then lowercase) ------------

export function parseArgs(argv: string[]): ParsedArgs | null {
  let email: string | undefined;
  let fullName: string | undefined;
  let allowAdditional = false;

  for (let i = 0; i < argv.length; i += 1) {
    const arg = argv[i];
    if (arg === '--email') {
      email = argv[i + 1];
      i += 1;
    } else if (arg === '--name') {
      fullName = argv[i + 1];
      i += 1;
    } else if (arg === '--allow-additional') {
      allowAdditional = true;
    }
  }

  if (!email || !fullName) {
    return null;
  }

  // Matches AuthService's normalizeEmail() exactly (trim + lowercase) —
  // without this, an ADMIN created here as "Admin@School.example" would be
  // stored with different casing than the normal login path looks up
  // ("admin@school.example"), making the account unable to log in.
  return { email: email.trim().toLowerCase(), fullName: fullName.trim(), allowAdditional };
}

--- Advisory-lock acquisition (surgical hotfix — $executeRaw, not
    $queryRaw, to avoid the void-deserialization defect; see section 0) ---

const BCRYPT_SALT_ROUNDS = 12; // Keep in sync with apps/api/src/auth/auth.service.ts
const MIN_ADMIN_PASSWORD_LENGTH = 12;

/** Fixed advisory-lock key serializing concurrent bootstrap invocations. */
const BOOTSTRAP_ADMIN_LOCK_KEY = 'tubi:bootstrap-admin';

/**
 * Acquires the transaction-scoped advisory lock that serializes concurrent
 * bootstrap invocations. Extracted into its own function so a test can
 * assert the exact call shape without a real database connection.
 *
 * Uses `$executeRaw`, not `$queryRaw`: `pg_advisory_xact_lock` returns
 * PostgreSQL `void`, and `$queryRaw` always tries to deserialize a result
 * set into typed columns — `void` has no such mapping, so it fails every
 * time with "Failed to deserialize column of type 'void'" (this was the
 * exact failure seen when this script was first run against production;
 * reproduced against a real database before this fix — see section 0).
 * `$executeRaw` executes the identical statement and reports only the
 * affected-row count, never attempting to deserialize a column — the lock
 * is acquired identically either way, and this fix changes nothing about
 * the transaction-scoped serialization semantics: the lock is still taken
 * inside the same `$transaction`, before either read, and is still
 * released automatically when that transaction commits or rolls back.
 */
export async function acquireBootstrapAdminLock(
  tx: Pick<Prisma.TransactionClient, '$executeRaw'>,
): Promise<void> {
  await tx.$executeRaw`SELECT pg_advisory_xact_lock(hashtext(${BOOTSTRAP_ADMIN_LOCK_KEY})::bigint)`;
}

--- Concurrency serialization + existing-ADMIN check + email-uniqueness
    check + password hashing + ADMIN creation + cleanup/error handling ---

async function main(): Promise<void> {
  const parsed = parseArgs(process.argv.slice(2));
  if (!parsed) {
    console.error(
      'Usage: node dist/scripts/bootstrap-admin.js --email <email> --name "<full name>" [--allow-additional]',
    );
    process.exitCode = 1;
    return;
  }

  const { email, fullName, allowAdditional } = parsed;

  if (!isEmail(email)) {
    console.error(`Not a valid email address: ${email}`);
    process.exitCode = 1;
    return;
  }
  if (fullName.length === 0) {
    console.error('--name must not be empty.');
    process.exitCode = 1;
    return;
  }

  const connectionString = process.env.DATABASE_URL;
  if (!connectionString) {
    console.error('DATABASE_URL is not set — refusing to guess a database to write to.');
    process.exitCode = 1;
    return;
  }

  // Password acquisition/validation happens before any database work: it
  // is interactive human I/O with no reason to hold an advisory lock (or
  // any transaction) open while waiting on it.
  const password = await resolvePassword();
  if (password.length < MIN_ADMIN_PASSWORD_LENGTH) {
    console.error(
      `Password must be at least ${MIN_ADMIN_PASSWORD_LENGTH} characters for an ADMIN account.`,
    );
    process.exitCode = 1;
    return;
  }
  const passwordHash = await bcrypt.hash(password, BCRYPT_SALT_ROUNDS);

  const prisma = new PrismaClient({ adapter: new PrismaPg({ connectionString }) });

  try {
    const result = await prisma.$transaction(async (tx) => {
      // Taking this lock BEFORE either read is what actually prevents the
      // race: two concurrent invocations cannot both pass the
      // existing-ADMIN check and then both insert. The second invocation
      // blocks here until the first transaction commits or rolls back,
      // then performs its own check against the now-current state — it
      // can never observe "no ADMIN exists" while another transaction is
      // also mid-flight toward creating one. See `acquireBootstrapAdminLock`
      // above for why this uses `$executeRaw`, not `$queryRaw`.
      await acquireBootstrapAdminLock(tx);

      const existingAdmin = await tx.user.findFirst({
        where: { role: RoleName.ADMIN },
        select: { email: true },
      });
      if (existingAdmin && !allowAdditional) {
        return { outcome: 'admin-exists' as const, existingEmail: existingAdmin.email };
      }

      const emailInUse = await tx.user.findUnique({ where: { email }, select: { id: true } });
      if (emailInUse) {
        return { outcome: 'email-in-use' as const };
      }

      const created = await tx.user.create({
        data: { email, passwordHash, fullName, role: RoleName.ADMIN, isActive: true },
        select: { id: true, email: true, createdAt: true },
      });
      return { outcome: 'created' as const, created };
    });

    switch (result.outcome) {
      case 'admin-exists':
        console.error(
          `An ADMIN account already exists (${result.existingEmail}). Refusing to create ` +
            'another without --allow-additional. This is a safety default, not a hard limit ' +
            '— pass --allow-additional if a second ADMIN is genuinely intended.',
        );
        process.exitCode = 1;
        return;
      case 'email-in-use':
        console.error(
          `A user with email ${email} already exists (any role) — choose a different email.`,
        );
        process.exitCode = 1;
        return;
      case 'created':
        console.log(
          `Created ADMIN user ${result.created.email} (id: ${result.created.id}) at ` +
            `${result.created.createdAt.toISOString()}.`,
        );
        return;
    }
  } finally {
    await prisma.$disconnect();
  }
}

--- Password acquisition (env var for non-interactive use, else unechoed
    interactive prompt with confirmation) -------------------------------

async function resolvePassword(): Promise<string> {
  // eslint-disable-next-line turbo/no-undeclared-env-vars
  const fromEnv = process.env.ADMIN_BOOTSTRAP_PASSWORD;
  if (fromEnv) {
    return fromEnv;
  }
  const first = await promptForPassword('Admin password (input hidden): ');
  const second = await promptForPassword('Confirm password: ');
  if (first !== second) {
    throw new Error('Passwords did not match.');
  }
  return first;
}

import { acquireBootstrapAdminLock, parseArgs } from './bootstrap-admin.js';

describe('acquireBootstrapAdminLock', () => {
  it('uses $executeRaw, never $queryRaw, for the void-returning advisory-lock call', async () => {
    // pg_advisory_xact_lock returns PostgreSQL `void`, which `$queryRaw`
    // cannot deserialize ("Failed to deserialize column of type 'void'" —
    // the exact production failure this test guards against). A fake
    // whose `$queryRaw` throws proves the fix never calls it for this
    // statement; `$executeRaw` returning a plain row-count (no
    // deserialization attempt) proves the call still succeeds.
    const queryRaw = jest.fn(() => {
      throw new Error('$queryRaw must not be called for a void-returning statement');
    });
    const executeRaw = jest.fn().mockResolvedValue(1);
    const tx = { $queryRaw: queryRaw, $executeRaw: executeRaw };

    await expect(acquireBootstrapAdminLock(tx)).resolves.toBeUndefined();

    expect(executeRaw).toHaveBeenCalledTimes(1);
    expect(queryRaw).not.toHaveBeenCalled();
  });

  it('locks on the same fixed key every call (transaction-scoped serialization is keyed, not per-invocation-random)', async () => {
    const executeRaw = jest.fn().mockResolvedValue(1);
    const tx = { $queryRaw: jest.fn(), $executeRaw: executeRaw };

    await acquireBootstrapAdminLock(tx);
    await acquireBootstrapAdminLock(tx);

    // Prisma's tagged-template raw-query helpers pass the interpolated
    // values as a strings array followed by the values themselves — the
    // lock key value must be identical (and non-empty) across calls, or
    // two invocations could take different locks and never actually
    // serialize against each other.
    const [, keyFirstCall] = executeRaw.mock.calls[0] as [TemplateStringsArray, string];
    const [, keySecondCall] = executeRaw.mock.calls[1] as [TemplateStringsArray, string];
    expect(keyFirstCall).toBe(keySecondCall);
    expect(keyFirstCall.length).toBeGreaterThan(0);
  });
});

    expect(result?.allowAdditional).toBe(true);
  });

  it('trims surrounding whitespace from email and name', () => {
    const result = parseArgs([
      '--email',
      '  admin@school.example  ',
      '--name',
      '  Founder Admin  ',
    ]);
    expect(result).toEqual({
      email: 'admin@school.example',
      fullName: 'Founder Admin',
      allowAdditional: false,
    });
  });

  it('lowercases the email to match AuthService.normalizeEmail, so the created account can log in', () => {
    const result = parseArgs(['--email', 'Admin@School.Example', '--name', 'Founder Admin']);
    expect(result?.email).toBe('admin@school.example');
  });

  it('lowercases and trims together, without altering name casing', () => {
    const result = parseArgs(['--email', '  Admin@School.Example  ', '--name', 'Founder Admin']);
    expect(result).toEqual({
      email: 'admin@school.example',
      fullName: 'Founder Admin',
      allowAdditional: false,
    });
  });

  it('returns null when --email is missing', () => {
    expect(parseArgs(['--name', 'Founder Admin'])).toBeNull();
  });

  it('returns null when --name is missing', () => {
    expect(parseArgs(['--email', 'admin@school.example'])).toBeNull();
  });

  it('returns null for empty argv', () => {
    expect(parseArgs([])).toBeNull();
  });
