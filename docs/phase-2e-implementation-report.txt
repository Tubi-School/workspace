B. TEACHER PROVISIONING ARCHITECTURE
================================================================================

TeachersService.create runs inside prisma.$transaction, creating the User
(role: RoleName.TEACHER, hardcoded — never read from the request) and its
TeacherProfile atomically; either both rows exist or neither does. Same
standards as Phase 2C's AuthService: email normalized via
trim().toLowerCase() before lookup/storage, password hashed with bcryptjs
at cost factor 12, a findUnique pre-check plus a P2002-catching fallback
both collapse to the identical 409 Conflict for a duplicate email (closing
the same registration race Phase 2C hardened). Every read returns a
TeacherWithUser shape built from an explicit Prisma select (id, email,
fullName, role, isActive, createdAt, updatedAt) — passwordHash is never
included in the query, so it structurally cannot leak. There is NO DELETE
ENDPOINT: a TeacherProfile may be referenced by Course.primaryTeacherId or
SessionTeacher at any time, so TeachersService.update supports
isActive: false as the controlled way to revoke access without destroying
those references (consistent with Phase 2D's deletion-safety convention).
email/password are not editable through UpdateTeacherDto in this
milestone — credential rotation is deliberately out of scope here.

================================================================================
E. SESSIONTEACHER / STAFFING BEHAVIOR
================================================================================

On creation, the PRIMARY teacher always defaults from
Course.primaryTeacherId; any requested assistantTeacherIds/
substituteTeacherIds are validated and attached in the same session.create
call via nested teachers: { create: [...] }. Every teacher id (including
the defaulted PRIMARY) is checked: 404 if the TeacherProfile doesn't
exist, 409 if it exists but its User is inactive or not role TEACHER.
Duplicate teacher ids across roles in one request are rejected (409)
before any database write.

Post-creation staffing goes through addTeacher/updateTeacherRole/
removeTeacher:
- adding a duplicate assignment is 409
- adding a second PRIMARY while one exists is 409 ("reassign or remove it
  first" — never silently replaced)
- removing the sole PRIMARY is 409
- demoting the sole PRIMARY to ASSISTANT/SUBSTITUTE is 409

RESOLVED BY THE CORRECTION PASS — atomic PRIMARY reassignment:
PATCH /admin/sessions/:id/primary-teacher (ADMIN only) reassigns PRIMARY
in one prisma.$transaction. Request body: { incomingTeacherId,
outgoingTeacherAction }, where outgoingTeacherAction is explicitly one of
BECOME_ASSISTANT, BECOME_SUBSTITUTE, or REMOVE — the outgoing teacher's
new state is never inferred. Preconditions, each independently checked
before the transaction opens: the session exists (404); the incoming
TeacherProfile exists (404) and belongs to an active TEACHER account
(409); the session currently has exactly one PRIMARY (409 otherwise); the
incoming teacher is not already the PRIMARY (409). Inside the transaction,
the outgoing teacher is updated to their new role or deleted from the
session first, then the incoming teacher is promoted — updated in place if
they already hold a non-PRIMARY assignment on the session (unambiguous,
avoids a duplicate-membership conflict), or given a fresh PRIMARY row
otherwise. Because both halves commit together, no caller can ever observe
an intermediate zero- or two-PRIMARY state, and a failure partway through
(verified by test — see section I) leaves the original staffing completely
unchanged.

================================================================================
F. SESSION LIFECYCLE BEHAVIOR
================================================================================

SCHEDULED -> LIVE -> ENDED and SCHEDULED -> CANCELED / LIVE -> CANCELED are
the only permitted transitions, each its own dedicated endpoint (markLive,
markEnded, cancel) rather than an arbitrary status field — UpdateSessionDto
carries no status. Any other requested transition (e.g. ENDED directly
from SCHEDULED, canceling an already-ENDED/CANCELED session) is rejected
with 409. cancel sets canceledAt = new Date(). PATCH /admin/sessions/:id
(schedule edits) is only permitted while status === SCHEDULED; once
LIVE/ENDED/CANCELED it's rejected with 409 — the schedule becomes part of
the historical record. No entitlement-snapshot or attendance-record
generation was implemented, per the brief.

================================================================================
G. REPLACEMENT-SESSION BEHAVIOR
================================================================================

A replacement is created by passing replacementForSessionId on
CreateSessionDto (a normal Session create — no separate endpoint). The
service validates the target exists (404), is CANCELED (409 otherwise),
and walks the target's replacementForSessionId ancestry chain with a
visited-set to reject a cycle (409) defensively — in practice a cycle
can't form through this API since replacementForSessionId is set only at
creation and never mutated afterward, but a corrupted chain is still
rejected rather than silently accepted. "At most one direct replacement"
is enforced by the EXISTING DB-LEVEL UNIQUE CONSTRAINT on
Session.replacementForSessionId (frozen schema, unchanged) — a second
attempt to replace the same target throws Prisma's P2002, caught and
translated to 409 Conflict. Entitlement copying is explicitly out of
scope and was not implemented.

H. VALIDATION / SECURITY RULES
================================================================================

Every controller uses @UseGuards(JwtAuthGuard, RolesGuard) + @Roles(...),
matching Phase 2D's convention exactly: ADMIN-only for all mutations
(teacher provisioning/update, session create/update/lifecycle/staffing),
ADMIN+TEACHER for reads, LEARNER excluded from everything in this
milestone. Error-code convention preserved: malformed UUID -> 400
(@IsUUID()/ParseUUIDPipe), valid UUID pointing to a missing entity -> 404,
business/uniqueness conflicts -> 409, unauthenticated -> 401, wrong role
-> 403. passwordHash cannot reach any response — both TeachersService and
SessionsService build their response shapes from explicit Prisma selects
that never include it, and no User internals beyond
id/email/fullName/role/isActive/createdAt/updatedAt are ever exposed.

L. WARNINGS / UNRESOLVED ISSUES
================================================================================

1. [RESOLVED by the correction pass] No atomic PRIMARY-reassignment
   operation. PATCH /admin/sessions/:id/primary-teacher now provides this,
   with the outgoing teacher's new state always explicit (never inferred)
   and the whole operation atomic. No further ambiguity remains on this
   point.

2. Business-rule status-code judgment calls, consistent with Phase 2D's
   own resolved precedent: sessionDate/academic-term-range validation
   failures use 400 (business input validation, like Phase 2D's
   AcademicTerm date-range check) rather than 409; a teacher that exists
   but is inactive uses 409 (state conflict) distinct from a teacher that
   doesn't exist at all (404) — mirroring the Phase 2D 400-vs-404
   correction's underlying principle.

3. startTime/endTime are trusted as absolute instants (new Date(iso)); the
   DTO requires ISO 8601 but doesn't enforce a Z/offset suffix — a client
   omitting one would have it interpreted per JS's ISO-parsing rules (UTC
   for date-only, but time-with-no-offset strings are also treated as UTC
   per the ECMAScript spec, so this is safe in practice, but worth calling
   out as an assumption).

4. The pre-existing Turbo `spawn UNKNOWN` issue remains unchanged and
   unrelated to this milestone.

5. No pagination on any findAll, consistent with the same known gap
   already flagged in the Phase 2D report.

implementing this correction.
